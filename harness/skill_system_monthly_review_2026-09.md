### 🟡 P1：daily_memory_capture 覆盖率下降（96.8%→86.7%）

**事实**：
- 8月：30/31天 = 96.8%（🟢）
- 9月：26/30天 = 86.7%（🟡）
- 缺失6天：9/4、9/5、9/8、9/9、9/13、9/22

**影响**：记忆捕获是T7最稳定的基础场景，覆盖率下降意味着监控基线在弱化

**建议**：
- 核查对应日期的日程执行日志，确认是日程未触发还是触发了但未写route_log
- 若是hook写入问题，参照风控新架构的hook方案修复
- 若是日程漂移，检查schedule配置

### 🟡 P1：Fallback统计口径偏差（监控字段定义与实际行为不一致）

**事实**：
- fallback_used 字段记录为 0（0%）
- 但实际发生了至少15次数据层面降级（MCP空返回→腾讯/akshare兜底）
- 原因：fallback_used 只记录"路由决策层面的降级"（换了工具/技能），不记录"数据层面的降级"（同工具内换源）

**影响**：
- T6 Fallback链评分虚高（看起来100%完美，实际有数据降级）
- 可能掩盖真实的降级率，影响健康度评估的准确性

**建议**：
- 方案A：新增 `data_fallback_used` 字段，区分路由降级和数据降级
- 方案B：在CONFIG.md中明确定义fallback_used的统计口径，T7报告中增加"数据降级率"指标
- 推荐方案B（成本低、见效快）

### 🟡 P2：iFinD MCP 健康检查失败率偏高（42.9%）

**事实**：
- ifind_mcp_health_check 14次中6次失败（42.9%）
- 但kline_fetch的成功率仍有94.6%（健康检查失败时仍能正常调用？）
- 9/24起连续6个交易日有"返回空"记录（与MEMORY.md中"iFinD MCP 9/24起连续6个交易日返回空"一致）

**影响**：
- 健康检查与实际可用性之间可能存在不一致
- MCP接口兼容性问题导致部分标的返回空，但三级兜底机制生效，未影响最终结果

**建议**：
- 非紧急，已有三级兜底（iFinD→腾讯→akshare）保障
- 在下一版MCP适配器中优化空返回处理逻辑
- T7报告中增加"数据源可用性"指标，独立于路由决策质量

### 🟡 P2：skill_patches 增长过快可能稀释质量

**事实**：
- 8月+24条（+42.1%），9月+39条（+48.1%）
- 总量从57条→81条→120条，两个月翻倍
- 新增patch的激活率、复用率、存活率尚未验证

**影响**：
- 数量快速增长但质量未知，可能存在低质量/重复patch
- T4 Patch激活评分（0.930）尚未经过真实场景验证

**建议**：
- 下月T7增加"patch激活率"和"patch存活率"统计
- 对超过3个月未激活的patch进行清理或降级
- 建立patch生命周期管理机制
