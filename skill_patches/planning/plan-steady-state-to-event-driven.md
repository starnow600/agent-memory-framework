# Planning: 稳态机制事件驱动转换

## Trigger
当一个周期性监控/审查机制（如每日review、每日巡检）进入"零发现稳态"（连续≥20次无主动行动/无通知）时

## Rule
连续运行的监控机制在达到"零发现稳态"后，应主动评估是否切换为事件驱动模式，避免无效计算和资源浪费：

### 触发转换的4个判定条件（全满足=可切换）
1. **连续零发现**：≥20次review/运行无新增失败、无新增纠正、无关键节点变化
2. **机制目的已达成**：原设计目标（如发现问题、及时通知）已通过其他方式覆盖（如专属日程、独立监控链）
3. **空间/资源压力**：持续运行导致资源消耗（如MEMORY空间紧张、token消耗）但产出边际为零
4. **有等效替代机制**：切换后不会产生监控盲区（如事件触发仍可唤醒、关键节点有独立日程）

### 转换决策树
```
连续零发现≥20次？
├─ 否 → 保持周期性运行
└─ 是 → 检查4个转换条件
    ├─ ≤2条件满足 → 保持+缩短运行频率（如日→周）
    └─ 全满足 → 切换事件驱动 + 设置唤醒触发器
```

### 唤醒触发器清单（切换事件驱动后必须配置）
- 新叙事出现（narratives/目录有新文件）
- 关键状态变更（持仓变动、regime切换、P0触发）
- 用户主动推送信息
- 外部事件（重大新闻、财报、政策）
- 定期唤醒检查（如每周1次快速扫描确认无遗漏）

## Why
8/3-8/9共7天Caveman双轨验证期内，每日凌晨review从第34次到第40次（7次全零发现），累计20连不通知。期间：①无新增失败/纠正 ②所有关键节点（forward_test/风控/持仓）均有独立日程覆盖 ③MEMORY空间持续在5000B边缘运行，每日capture压缩占用token但产出为零。8/9决定切换事件驱动模式——机制的目的是"发现问题"，不是"运行本身"。当连续无问题被发现时，机制本身就是最大的问题。

## Anti-pattern
- ❌ "机制必须一直跑"（运行=有效是错觉，产出才是目的）
- ❌ 切换事件驱动后无唤醒触发器（变成彻底静默=监控盲区）
- ❌ 用"万一呢"拒绝切换（风险偏好≠无差别防御）
- ❌ 稳态期仍维持高频运行（token/空间/注意力资源浪费）
