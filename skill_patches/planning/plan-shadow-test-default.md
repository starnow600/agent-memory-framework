# plan-shadow-test-default（影子测试默认方法论）

**层级**: Planning
**ID**: plan-shadow-test-default
**触发**: 任何"新能力/新算法/新流程想替代旧系统"的场景
**来源**: 8/30主人点破"影子测试出现过很多次但每次都从零做计划" + 风控技能编码4周影子测试方案 + 数据源切换(8/20) + PlugMem升级(8/23-8/26) + 索引同步迁移(8/17)

---

## 模式描述

新能力替换旧系统时，默认走**影子测试三步走**，禁止直接切换或"先上了再说"。

### 三步走框架

**Step 1: 并行跑（影子模式）**
- 两套系统**共用输入、独立输出**
- 每日自动生成diff报告
- 影子版只读、不影响主流程、幂等

**Step 2: 达标转正**
- 预设验收标准（核心硬指标 + 提升指标 + 否决项）
- 达标前不转正，不拍脑袋
- 设Gate机制（编码完成→Week1稳定→Week3校准→最终验收）

**Step 3: 旧版降级为fallback**
- 不直接删除旧版
- 留作兜底回滚方案
- 观察期（建议2-4周）确认无问题后再归档

### 适用场景（满足两个条件即可）
1. 有明确的**输入输出**（能并行跑）
2. 有可衡量的**好坏标准**（能对比）

### 覆盖类别
| 类别 | 例子 |
|------|------|
| 量化/投资 | 风控策略、选股模型、数据源切换、止损算法 |
| 记忆系统 | 检索算法升级、新增记忆层、提取方式变更 |
| 技能/工具 | 新技能替换旧流程、API切换、CLI升级 |
| 系统架构 | 流水线改造、调度方式变更、索引重建 |
| 流程规则 | 格式规范调整、输出模板变更、质量标准升级 |

## 为什么有效

- **避免切换即事故**: 影子模式下新系统的bug不会影响主流程，风险隔离
- **数据驱动决策**: 达标了才转正，不靠"感觉应该没问题"
- **兜底安全**: 旧版留作fallback，出问题秒切回去
- **历史验证**: 至少3次成功先例（数据源切换69分钟闭环、PlugMem Phase1→2迭代、索引同步mtime修复），都是"先并行验证再切主"的模式

## 影子测试两阶段节奏

影子测试不只是"等结果"的等待期，更是**低成本快速迭代的黄金窗口**。典型4周分为两个阶段：

### 阶段一：加速迭代期（前2周）
- 发现问题、补充功能、优化体验，**鼓励快速迭代**
- 新发现的bug/优化点立即修复，不攒到转正后
- 可以发布多个小版本（如v2.0→v2.0.1→v2.0.3），只要核心框架不动
- 目标：把能想到的问题都暴露并修掉

### 阶段二：收敛稳定期（后2周）
- 主要做稳定性验证，**减少变更频率**
- 不再大改功能，只修严重bug
- 观察指标是否稳定、波动是否在可接受范围
- 目标：确认系统能持续稳定运行，具备转正条件

> 核心洞察：影子期的新系统是"隔离沙箱"，改坏了不影响主流程→所以前2周应该大胆迭代快速完善，而不是等到转正后再改（那样风险反而更大）

## 关键参数（可调整）

- 影子测试周期：典型4周（1月稳定期足够暴露大部分问题）
- 加速迭代期：前2周（可根据复杂度调整）
- 收敛稳定期：后2周
- Gate数量：建议3-4个（编码完成→Week1→Week3→最终验收）
- 核心硬指标数量：3-5个（一致性、完整性、漏报、误报等）
- 观察期：转正后2-4周，确认无误后再归档旧版
