# plan-global-inventory-first

**架构升级先做全域盘点，再从最痛的模块开始——局部最优不是全局最优**

## 触发条件
启动架构类项目（代码重构/架构升级/机制优化）时，尤其是"渐进式披露""模块化""统一配置"这类跨模块的架构原则

## 问题模式
做架构升级时，第一反应是先啃最大的模块（通常是风控），把"架构原则"降级成了"某模块的优化项目"。具体表现：
- 注意力被最显眼的痛点吸引（最大的脚本/最多的代码/最频繁的失败）
- 做完一个模块后觉得"差不多了"，但架构原则没有在全域落地
- 用户指出"其他模块呢"才意识到视角窄了
- 同一种思维惯性在不同架构项目中反复出现（S2加固、变更管理、渐进式披露……都是先风控后全域）

## 三步法

### Step 1：全域盘点（必须在动手前完成）
- 列出受该架构原则影响的所有模块/技能/脚本
- 标记每个模块的当前状态（已符合 / 部分符合 / 不符合 / 不适用）
- 统计覆盖率：多少模块已经有该形态，多少需要改造

### Step 2：优先级排序（不是"从风控开始"，是"从影响最大的开始"）
- 按影响/风险/依赖度排序，而非按代码量或熟悉度
- 风控如果是最大模块，可能排第一，但必须是排序出来的，不是默认的
- 标记需要统一的跨模块依赖（共享配置、通用函数、探测规则）

### Step 3：分批实施 + 全域验收
- 按优先级分批实施，但每批结束后都回到Step 1核对覆盖率
- 最后必须有"全域覆盖验收"——确认原则在所有适用模块都落地了
- 对于"不适用"的模块，要说明理由，不能因为忘了就归到"不适用"

## 为什么这是Planning层
- 这是任务级的组织结构决策：做一个架构项目，应该先盘点再动手，而不是上来就写代码
- 它决定了"做什么、按什么顺序做"，而不是"怎么做某一步"
- 典型的规划错误——方向窄了，后面做得再好也是局部最优
