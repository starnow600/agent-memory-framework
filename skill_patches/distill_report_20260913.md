## 二、新增Patch详解

### Planning层：plan-boundary-calibration-principle

**职责边界校准原则——单点反馈→全体系校准**

**来源叙事（因果链）**：
- 触发点：9/10月度自检初始评分80分，主人指出"止损纪律扣分是越界判断——决策权在你，我只负责监控提醒"
- 展开：不只是止损纪律这一项，整个评估体系都有越界倾向——把用户决策的结果归因为agent自身的失败
- 行动：全体系扫描26处越界表述，9月报告7处（80→86分）、8月报告11处（88→93分）、叙事Review 8处
- 固化：写入MEMORY.md核心规则 + S1加决策建档检查（防止再次越界）

**核心洞察**：用户指出一处越界，不能只修那一处。越界判断反映的是元认知层面的自我定位偏差，必须做全体系校准——扫描所有相关产出、重新校准评分基线、在规则层固化边界。单点修正治标不治本。

**叙事的作用**：
- 仅凭memory_search搜"越界""职责"只能找到9/10当天的对话，会以为这是一个单点问题
- 叙事串联起"9/10初始评分→主人纠正→26处全量修正→8月报告同步校准→规则层固化"的完整因果链
- 从因果链中提炼出"单点反馈→全量扫描→基线重校→规则固化"的四步法模式，而非"修一个bug"的原子级修复

---

### Functional层：func-s1-lite-expand-to-scheduled-reports

**S1-Lite扩展到日程产物交付——越自动化的产出越需要质量卡点**

**来源叙事（因果链）**：
- v1.0诞生：9/7 PPT 7轮迭代教训 → 改完不验=返工 → S1-Lite（修改类交付必做反向验证）
- v1.5扩展：9/9 日程配置教训 → 改了description但script_path没清 → 配置修改也需要反向验证
- v2.0升级：9/11 自检发现"S1今日0次" → 日程触发的报告交付全跳过S1 → 主人确认扩展到日程报告

**核心洞察**：S1-Lite的覆盖面是自然生长的——从"修改类交付"到"配置类修改"再到"日程报告交付"。底层逻辑一致：**最小可行卡点 + 高频执行 > 完美checklist + 低频执行**。越是自动化的产出，越容易默认"脚本是对的"而跳过自检，反而更需要补机制上的校验卡点。

**叙事的作用**：
- 仅凭memory_search搜"S1-Lite"只能找到各条独立的记录（PPT教训、日程教训、0次发现），看不到它们之间的演化关系
- 叙事揭示了S1-Lite的三阶段成长路径（v1.0→v1.5→v2.0），每个阶段都有明确的触发事件和扩展逻辑
- 从演化路径中提炼出"S1-Lite适用场景自然扩展"模式——不是一次性设计好所有场景，而是遇到一个盲区补一个
- 这是"自生长规则体系"的典型案例：规则不是设计出来的，是在踩坑中长出来的

### Atomic层1：atom-sdk-exception-bypass

**SDK层异常绕过业务层容错——容错链的前置入口不能被堵死**

**来源叙事（因果链）**：
- 现象A：9/8-9/9每日自检CodeAct沙箱挂 → sessions_list工具不存在 → SDK层抛错 → 业务层try-catch接不住
- 现象B：9/8 iFinD v6.1.2启动超时修复 → 启动阶段token获取失败 → 降级逻辑跑不到 → 加启动超时熔断
- 共性：两个看似不相关的故障（一个是工具缺失，一个是数据源超限），底层是同一个模式——**容错链的前置环节失败，后面的降级逻辑都失效**
- 解决思路同源：在最外层加兜底，保证容错链的入口不被堵死

**核心洞察**：所有"多级降级""三级兜底"的设计，都隐含了"程序能启动到降级逻辑"这个前提假设。如果错误发生在SDK层/启动阶段/初始化环节，业务层的容错设计再完善也没用。必须在最外层加兜底捕获，并在新环境迁移时验证最坏路径。

**叙事的作用**：
- 仅凭memory_search搜"CodeAct报错"和"iFinD超限"会得到两条独立的失败记录，看不到它们的共性
- 叙事将两个不同场景的故障串联起来，提炼出共同的底层模式（SDK层异常绕过业务层容错）
- 这是"跨事件模式识别"的典型案例——模式不在单个事件里，而在事件之间的结构相似性里
- 如果没有叙事的因果串联，这两个故障只会各产生一个单点修复，不会升华为通用的架构原则

### Atomic层2：atom-schedule-config-verify

**日程配置修改后必须反向验证——description ≠ 实际执行模式**

**来源叙事（因果链）**：
- 触发：9/8每日自检挂了 → 当晚决定改回主agent触发 → 改了schedule的description
- 重复失败：9/9又挂了 → 排查发现只改了description，script_path没清除 → calendar_update无法清除script_path
- 解决：删除旧日程 + 重新创建纯工单模式日程
- 认知升级：description是给人看的，不是给系统执行的。改完不验=没改

**核心洞察**：修改配置时，人容易把"我改了"等同于"生效了"，特别是当description写得很详细时，语义上会误导人以为这就是配置本身。必须用查询API反向验证实际执行字段（script_path/rrule/script_args），信查询结果不信自己的感觉。模式切换类修改优先用删除重建而非修改，因为API可能有字段限制。

**叙事的作用**：
- 仅凭memory_search搜"日程修改失败"只能找到9/9的修复记录，看不到"第一天失败→尝试修复→第二天又失败→才找到根因"的完整过程
- 叙事还原了完整的踩坑-重试-再踩坑-解决的弧线，从中提炼出"description≠执行模式"的核心教训
- 完整的失败弧线比单个失败点更有价值——它展示了人是如何被误导的（description的语义误导），以及为什么会重复踩坑
- 这个patch的价值不只是"改完要验证"，更是揭示了"为什么人会忘了验证"——被description的语义暗示骗了

### 追踪策略改进建议

**建议1：T7监控补路由hook（高优先级）**
- 问题：核心任务（风控/全市场扫描/专家影子测试）迁到CodeAct后绕过route_log，T7监控名存实亡
- 改进：给3个核心任务补路由hook，或改造T7监控锚定业务目标而非执行路径
- 建议参考atom-monitoring-coverage-drift patch的约束：监控指标锚定业务目标（如"风控任务执行成功率"），而非实现路径（如"route_log中风控条目数量"）
- 状态：待主人决策（方案A降频 vs 方案B补hook）

**建议2：追踪报告的"静默阈值"机制（中优先级）**
- 现象：叙事Review连续零发现（事件驱动后68次中仅2次有行动项），导致日报价值下降
- 已执行：合并入月度元认知自检（9/10决策）
- 可推广：其他追踪类任务（如T7、话题追踪）也应设置"连续N次零发现则降频"的机制
- 原则：追踪频率应该与事件密度匹配，而不是固定不变

**建议3：资源约束下的降级追踪（低优先级）**
- 现象：iFinD月初超限导致full模式连续失败，但fast模式兜底正常
- 改进：追踪报告中增加"资源状态"维度（如iFinD配额使用率、降级次数），提前预判周期性约束
