## 二、新增Patch详解

### Planning层：plan-stabilize-before-expanding

**基础不扎实不扩展原则——先夯实再扩张，流沙上盖楼必塌**

**来源叙事（因果链）**：
- Phase 3决策门（9/15）：S1/S2试点压线达标（问题减少率37.5%），结论"调整后扩展"，计划9/22启动S3+S4
- S2=0事件（9/18）：每日自检S2=0条（预期5条），大幅异常
- 排查发现（9/19）："纯工单=主agent执行"是错误假设 → CalDAV工单默认子agent跑 → 子agent质量不稳定（6→3→5→0条波动）
- 决策：S3+S4延期，先加固S2 → CodeAct主体+文件探测fallback+周校准双层架构 → 连续2周达标后再扩展
- 出口条件：完整度≥95% + 真实问题率≤5% + 连续2周

**核心洞察**：扩展的冲动是天然的——觉得"做更多=进步"。但如果基础能力还不稳定，扩展的结果是问题被放大、排查更难、维护成本指数增长。**稳定基础的价值是乘数效应**——基础稳定性从50%提到95%，所有上层功能的可靠性都跟着翻番。宁可慢一步把底打牢，也不要在流沙上盖楼。

**叙事的作用**：
- 仅凭memory_search搜"S2延期""S3推迟"只能找到9/19当天的决策记录，会以为这是一个单点问题
- 叙事串联起"Phase3决策门→计划扩展→S2=0异常→排查发现假设错误→推翻原计划→加固方案"的完整因果链
- 从因果链中提炼出"评估稳定性→找根因加固→达标后再扩展"的三步法模式，而非"出了bug修bug"的原子级响应
- 更重要的是，叙事揭示了这不是第一个案例——影子测试（plan-shadow-test-default）也是"先验证再转正"的同源逻辑，只是适用场景不同。如果没有叙事的因果串联，这两个模式会被当成独立事件，不会升华为通用的架构原则

### Functional层：func-optimization-uncovers-bugs

**优化即bug发现机制——重构/优化是发现深层bug的契机，不是纯性能工作**

**来源叙事（因果链）**：
- DAG化立项（9/13）：目标是消除v4.5评分引擎的3-4次重复计算，提升性能
- 开发过程中意外发现：v4.5存在全局状态泄漏（`_REVERSAL_SECTOR_WIN_RATE`、`_current_regime`等），导致多次运行结果不一致
- 对比验证：DAG模式因为无状态，反而更稳定；10/10合成数据通过，影子模式准备就绪
- "事件即规则"原则（系统提示词对标产出）：每次失败立即提取原子补丁，不等每周汇总 → 优化中的发现也应该即时纳入

**核心洞察**：优化/重构特别容易发现bug，因为它需要"重新审视"代码结构——站在更高的抽象层次看，最容易发现日常习以为常的问题。对比测试（新旧版本diff）本身就是最好的bug探测器。应该把"发现隐藏bug"作为优化任务的标准产出之一，而不是"额外工作"。

**叙事的作用**：
- 仅凭memory_search搜"DAG bug"只能找到"DAG化发现了状态泄漏"的单点记录，看不到这个模式的普遍性
- 叙事串联起"Inkwell清理顺带发现配置不一致→代码审计发现7个P0 bug→DAG化发现全局状态泄漏"的多个案例
- 从多个案例中提炼出"优化/重构/清理 → 深度审视 → 发现隐藏bug"的通用模式
- 这是"事件即规则"原则的工程化落地——不只是失败事件，优化过程中的发现也应该即时沉淀

### Atomic层1：atom-ticket-executor-assumption

**工单执行主体假设验证——description不决定执行主体，别把假设当设计依据**

**来源叙事（因果链）**：
- 背景（9/9）：每日自检从CodeAct改回纯工单模式，以为"主agent执行"，因为description写了"主agent触发"
- 现象1（9/10-9/18）：S2条数大幅波动——6条→3条→5条→0条，不可预测
- 排查（9/19）：calendar_get确认日程始终是纯工单模式，没有漂移 → 意识到"纯工单=主agent执行"是错误假设 → CalDAV工单默认子agent跑
- 验证：S2条数波动正好对应子agent质量不稳定的特征——时好时坏，个体差异大
- 结论：纯工单模式不可靠，质量要求高的任务不能用

**核心洞察**：description是给人看的，不是给系统执行的。系统调度看的是真正的执行字段（script_path、rrule等），不是description。如果把description里的"主agent执行"当成了事实，就会在错误的假设上建整个体系，等到出了大问题才发现地基是歪的。

**叙事的作用**：
- 仅凭memory_search搜"纯工单 子agent"只能找到9/19的修复记录，看不到完整的认知修正过程
- 叙事揭示了从"以为是日程漂移"到"发现是认知错误"的完整排查链条，以及中间走过的弯路
- 从叙事中提取出"执行主体必须验证，不能假设"的通用约束
- 这个模式与atom-schedule-config-verify（改完配置要验证）和atom-sdk-exception-bypass（前置环节失败）是同类问题——都是"前置假设错误导致整个链条失效"，但叙事把它们串联起来，形成了"假设验证"的家族认知

### Atomic层2：atom-cross-day-date-alignment

**跨天任务日期对齐——执行日≠覆盖日，匹配前先明确日期基准**

**来源叙事（因果链）**：
- 背景：每日记忆捕获在D日凌晨执行，覆盖D-1白天内容 → 文件名用D-1日期
- 问题：每日自检在D日晚间执行，文件探测fallback匹配的是"当天日期" → 匹配不到记忆捕获的产出 → 误报partial
- 9/17 S2就报了记忆捕获partial，但一直以为是"捕获任务没跑"
- 9/19 S2加固深度排查才发现：是日期匹配逻辑搞反了 → 修正后9/17 partial改为pass，9/18 S2补录5条

**核心洞察**：每个跨天任务都有两个日期维度——执行日期和覆盖日期。如果变量名只叫`date`不明确基准，很容易搞混。匹配失败时第一个应该查的就是"日期基准对不对"，而不是"任务是不是没跑"。

**叙事的作用**：
- 仅凭memory_search搜"日期匹配 bug"只能找到9/19的修复记录，看不到这个bug隐藏了多久、造成了多少误报
- 叙事揭示了这个bug从9/17就开始存在，连续几天误报partial，但因为"partial看起来正常"而没被深究
- 从叙事中提取出"日期变量必须明确基准""匹配失败先查日期"的通用约束
- 如果没有叙事串联，这只会被当成"一个小bug修了就完了"，不会升华为跨天任务的通用设计原则
