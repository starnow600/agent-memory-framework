# atom-sdk-exception-bypass（SDK层异常绕过业务层容错）

**层级**: Atomic
**ID**: atom-sdk-exception-bypass
**触发**: 代码/脚本在新环境（CodeAct沙箱、新SDK、新API）中运行时，容错逻辑失效
**来源**: 9/8-9/9每日自检CodeAct沙箱中`sessions_list`工具不存在 → SDK层直接抛错未进入业务层try-catch → 脚本容错设计失效

---

## 失败模式

脚本/代码在内部做了完善的容错设计（try-catch多个工具依次尝试、降级策略），但如果错误发生在**SDK层**（工具不存在、API不兼容、环境变量缺失），异常会在SDK调用时直接抛出，根本进不到业务逻辑层的try-catch中。

结果就是：**内部容错设计再完善，外部环境不支持就全白搭**。

### 典型场景
- CodeAct沙箱中某个工具不存在 → SDK调用层直接抛错 → 业务层try-catch接不到
- 新API版本变更了参数格式 → SDK解析失败 → 业务层的参数校验逻辑根本跑不到
- 环境变量缺失导致SDK初始化失败 → 后续所有容错逻辑都没机会执行
- 子session沙箱与主session工具集不同 → 同一段代码在主session正常在子session挂

### 为什么会被忽视

1. **开发环境=运行环境的隐含假设**：在本地/主session测试时工具都存在，想当然认为目标环境也有
2. **容错设计的"向内视角"**：只考虑了"业务逻辑出错怎么办"，没考虑"程序根本启动不了/工具根本调不到怎么办"
3. **SDK层错误的不可见性**：SDK层错误通常是神秘报错（如`tool not found`、`undefined`），不是业务层能识别的错误类型

## 约束

1. **新环境部署前必须做工具/API可用性清单比对**
   - 列出代码依赖的所有工具/API
   - 与目标环境的可用工具清单逐一比对
   - 缺失的工具必须有替代方案或明确的降级路径

2. **SDK调用外层必须有一层兜底异常捕获**
   - 在最外层SDK调用处加一层通用异常捕获（catch-all）
   - 捕获后进入降级流程（跳过后续步骤、返回默认值、记录错误）
   - 不能依赖业务层的try-catch来接住SDK层错误

3. **启动阶段的容错是第一优先级**
   - 程序启动/初始化阶段的错误最致命（后面的逻辑都跑不到）
   - 启动阶段必须有超时熔断（如token获取10秒超时立即降级）
   - 所有初始化步骤都应该有失败降级方案，不能让启动失败=全程序挂掉

4. **迁移到新执行环境时，必须验证"最坏路径"**
   - 不能只验证happy path（所有工具都可用、所有API都正常）
   - 必须验证：核心工具不存在时，降级逻辑是否真的能跑通
   - 方法：模拟工具缺失/API失败，看程序是否能优雅降级

### 与"启动级故障vs调用级故障"的关系

这是iFinD v6.1.2修复（启动级故障修复）的更通用抽象：
- iFinD案例：启动阶段token获取失败 → 降级逻辑跑不到 → 启动超时熔断修复
- CodeAct案例：SDK层工具不存在 → 业务层容错接不到 → 需要SDK层兜底捕获
- 同一个底层模式：**容错链的前置环节失败，后面的降级逻辑都失效**
- 同一个解决思路：**在最外层加兜底，保证容错链的入口不被堵死**

---

## 为什么重要

9/8-9/9连续两天每日自检挂在CodeAct沙箱的`sessions_list`缺失上。脚本内部明明有容错设计（自动补录失败也不影响主流程），但因为错误发生在SDK层，try-catch根本没接住。

这不是某一个工具的问题，而是一个**普遍的架构盲区**：所有"多级降级"、"三级兜底"的设计，都隐含了"程序能启动到降级逻辑"这个前提假设。如果前置环节（SDK初始化、工具可用性、启动参数）出问题，整个容错链都失效。

## Anti-pattern
- ❌ 只在业务层加try-catch，假设SDK调用肯定能进（SDK层错误会绕过所有业务层容错）
- ❌ "开发环境有=运行环境也有"的隐含假设（不同沙箱/环境的工具集可能不一样）
- ❌ 迁移到新环境只测happy path（不测降级路径、不测最坏情况）
- ❌ 把SDK层错误当偶发事件忽略（这是系统性盲区，不补的话下次换环境还会踩）
