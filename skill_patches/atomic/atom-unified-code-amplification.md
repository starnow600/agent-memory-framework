# atom-unified-code-amplification

**代码统一（从多份变成一份）会放大bug的影响面——统一消除重复的同时，一份代码两边都坏；每次统一必须伴随更严格的验证**

## 触发条件
将重复代码合并为单一事实来源（SSOT, Single Source of Truth）时；将多份配置/规则/探测逻辑统一到一个模块时

## 规则
"统一即放大"是架构工作的基本规律：

1. **收益与代价对称**：统一的收益是"改一处两边生效"，统一的代价是"有一处bug两边都坏"。收益多大，风险就有多大。

2. **验证强度要升级**：从多份变成一份时，验证标准不能还是"以前那份的标准"。必须：
   - 对统一后的模块做**单元测试**（覆盖每个函数/每条规则）
   - 对每个**消费方**做集成验证（确认两边引用的都是同一个且结果正确）
   - 特别检查**异常路径**：try/except包裹的代码，异常是否被静默吞掉

3. **隐性bug浮出水**：统一前可能两份代码各有各的bug但互相掩盖（一份有一份没有=有时好有时坏），统一后bug变成确定性的。这不是"统一导致了bug"，是"统一暴露了bug"。

4. **try/except Exception 是bug的藏身之所**：探测类/容错类函数常用try/except包裹，但如果异常被静默吞掉（不打log不告警），函数失效了也没人知道。统一后的代码如果有这个问题，影响范围更大。
   - 修复原则：探测类函数的异常至少打warning log，不能静默return False
   - 最好有监控告警：连续N次探测失败时触发

## 为什么是Atomic层
这是代码统一/架构整合时的具体约束——每一次"把多份变成一份"的操作，都要记住这个原则并升级验证。它是单架构动作的扩展约束。
