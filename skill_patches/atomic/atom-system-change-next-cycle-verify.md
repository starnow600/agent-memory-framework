# atom-system-change-next-cycle-verify（系统变更必须在下次执行周期验证）

**层级**: Atomic
**ID**: atom-system-change-next-cycle-verify
**触发**: 任何涉及系统行为变更的操作（启停任务/改规则/切换模式/更新配置）
**来源**: 10/2影子测试双触发路径（停了日程但cron还在跑，4天没人发现） + 10/4幽灵运行真相（变更后从未验证是否真的生效） + 9/9日程配置改description不生效（也是没验证）

---

## 失败模式

执行了系统变更（停任务、改配置、换模式）后，**没有在下次执行周期验证变更是否真的生效**，导致"以为改好了实际没改"的状态持续存在，直到被偶然发现。

### 典型场景

1. **停任务不验证**：停了一个日程，但功能还有其他触发路径（cron/其他任务联动/脚本内调用），任务实际还在跑
2. **改配置不验证**：改了配置文件/日程参数，但实际执行逻辑没变（比如只改了description，没改script_path）
3. **切换模式不验证**：宣称"切到了新模式"，但实际还在走旧逻辑（切换逻辑有bug，或者入口没全覆盖）

### 为什么会漏

1. **反馈延迟**：下次执行可能是第二天/下周，中间时间差让人忘了要验证
2. **入口盲区**：一个功能可能有多个触发入口，只验证了最显眼的那个
3. **确认偏误**："我改了肯定对"，倾向于相信自己的操作而不是去验证
4. **缺少验证钩子**：没有机制提醒"变更后要验证"，全靠自觉

---

## 约束

### 1. 变更后必须设置"验证提醒"

- 变更执行完毕后，立即在待办清单中添加"验证X变更是否生效"
- 验证时间 = 下次执行时间（如果是每日任务→次日验证；每周任务→下周验证）
- 验证项必须覆盖**所有已知入口**，不能只验一个

### 2. 验证标准

验证不是"看一眼差不多"，必须有明确的通过标准：

- **启停类**: 查询所有触发入口的状态（日程列表 + cron列表 + 脚本内开关变量），确认全部处于目标状态
- **配置类**: 查询实际生效的配置值（不是配置文件内容，而是运行时读取的值），确认与预期一致
- **模式切换类**: 实际运行一次，确认输出/行为符合新模式特征，没有旧模式残留

### 3. 验证结果必须记录

- 验证通过 → 更新锚点状态为✅ + 附验证依据
- 验证不通过 → 立即排查 + 记录失败原因 + 重新执行变更 + 设置下一次验证
- 不能"验证了但没写下来"——没有记录=没有验证

### 4. 多入口变更的验证原则

如果一个功能有多个触发入口（如日历日程 + CodeAct cron + 其他任务联动）：
- 变更前先盘点所有入口（见plan-change-impact-and-verify Step 1）
- 验证时逐个确认，**缺一个都不算通过**
- 盘点时不确定是否有其他入口 → 视为有，进一步排查

---

## 为什么重要

本周内同类问题出现了3次（S2三问题/双触发路径/幽灵运行），横跨3个不同领域，但失败模式完全一样：

- 改了一端 → 没改另一端 → 没验证 → 过了很久才发现

如果有"变更后必须验证"的硬性约束，这些问题都能在1天内发现，而不是拖3-5天。

更隐蔽的危害是**漂移累积**：每次变更加一点偏差，时间久了系统的"文档状态"和"实际状态"之间会出现巨大鸿沟，到时候修都不知道从哪修起。

## Anti-pattern

- ❌ 改完就不管了（"我都执行了还能错吗？"——能）
- ❌ 只验证一个入口（"主入口停了就行"——其他入口可能还在跑）
- ❌ 看一眼输出就说"应该生效了"（必须有明确的验证标准）
- ❌ 验证不通过不记录（下次还会踩同一个坑）
- ❌ 把"残留实例"当解释（不排查根因，用侥幸心理掩盖问题）
