# Atomic: MEMORY空间100B红线

## Trigger
MEMORY.md剩余空间接近上限时（任何写入操作前）

## Rule
- **100B红线**：剩余空间<100B（约<2%）必须触发主动压缩，禁止被动等待溢出
- **500B健康线**：目标维持在>500B（>10%）余量，给突发事件留缓冲
- **压缩优先级**：状态覆盖>标题精简>时效性条目删除>正文压缩（详见func-memory-active-compression）
- **🔒规则不可删**：标记为🔒的规则只能精简措辞，不能整条删除
- **压缩必留痕**：每次压缩操作必须记录"删了什么/为什么删/释放了多少B"

## Why
8/6 MEMORY达到5119/5120B（剩余**1B**），处于"任何新写入都可能截断"的极度危险状态。虽然最终通过主动压缩释放了458B安全脱险，但"剩1B才发现"本身就是风险——如果当日新增内容较多，可能在压缩完成前就发生截断。100B红线的设计：在还剩2%空间时就预警并启动压缩，留出缓冲。

本质：MEMORY空间管理不是"满了才管"的被动响应，而是"提前预警+主动释放"的主动管理。与ATR止损同理——等跌破了才止损，不如设一个安全边际提前动手。

## Source
- 8/5 daily capture：5021/5120B（剩余99B，首次触发"空间紧张"标注）
- 8/6 daily capture：5119/5120B（剩余1B，极其紧张，险些溢出）
- 8/7 daily capture：主动压缩释放458B，回到4661B（安全）
- 8/8 daily capture：5010B（剩余110B，回到红线以上但仍紧张）
- 8/9 daily capture：5026B（剩余94B，再次跌破红线）

## Anti-pattern
- ❌ 等溢出了才压缩（到1B时已无操作空间）
- ❌ 为腾空间删🔒规则（规则价值>空间价值）
- ❌ 压缩不留痕（无法回溯判断删错了没有）
- ❌ 每次只释放几十B（边际效率低，应一次释放200B+回到健康线）
