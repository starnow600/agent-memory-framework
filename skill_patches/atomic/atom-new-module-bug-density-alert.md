# atom-new-module-bug-density-alert（新模块bug密度预警）

**层级**: Atomic
**ID**: atom-new-module-bug-density-alert
**触发**: 新模块/新功能上线（特别是影子测试期内的新增复杂模块）后，短时间内连续发现bug时
**来源**: 9/3-9/4风控专家版v2.0新M6模块上线2天内发现2个逻辑bug（价格口径不一致+指数判断错误），密度偏高，review标记为"再发现1个触发阈值"

---

## 失败模式

新功能/新模块上线后，初期bug密度高是正常的，但如果短时间内（如上线3天内）连续发现≥2个逻辑级bug，说明**测试覆盖度不足**，需要主动加强测试流程，而不是"发现一个修一个"被动等待。

### 典型信号
- 上线3天内 ≥2个逻辑级bug（非UI/格式类）
- bug之间根因不同（说明不是同一个问题的连锁反应，是整体测试不足）
- 每个bug都可能导致核心判断错误（P1/P0级影响）

### 为什么会出现
1. **新模块复杂度高**：如LLM+搜索的深度分析模块，涉及多数据源交互，测试难度大
2. **冒烟测试覆盖不够**：只测了正常流程happy path，没测边界情况
3. **缺乏集成测试**：单模块功能正常，但和主系统集成后出问题（如价格口径不一致 = LLM用了不同数据源）
4. **复用旧逻辑时假设错误**：如复用"000开头=指数"的旧判断，没验证新场景下是否成立

---

## 约束

1. **密度阈值：上线3天内 ≥2个逻辑级bug = 触发预警**
   - 逻辑级bug = 影响核心判断/计算结果的bug
   - 排除：格式问题、文档缺失、性能优化（不影响正确性的）

2. **触发预警后必须做的3件事**
   - **代码复审**：对整个新模块做一次完整code review，重点关注边界条件和数据一致性
   - **补充冒烟用例**：针对已发现的bug类型扩展测试用例（如价格口径、代码判断各加1条用例）
   - **检查与主系统的集成点**：新模块和主系统之间的数据传递、接口调用是否有一致性保证

3. **如果3天内 ≥3个逻辑级bug = 升级为系统性问题**
   - 暂停新功能的进一步开发，先集中解决质量问题
   - 考虑是否需要回滚或降级新模块
   - 评估是否需要引入更严格的测试流程（如单元测试覆盖率门槛）

4. **影子测试期是发现bug的好时机，但不是降低质量的借口**
   - 影子测试发现bug说明影子测试在起作用，这是好事
   - 但bug密度过高说明测试流程有缺陷，需要改进
   - 目标是：影子测试期发现的bug是"真实场景才会暴露的边缘问题"，而不是"基本功能都没测到位"

---

## 为什么重要

2天2个bug，如果只是被动地"发现一个修一个"，可能还会有第3、第4个。主动预警可以在问题扩大之前加强测试覆盖，减少后续bug数量。特别是在影子测试期，质量问题不会影响生产，但如果带着一堆bug转正，就是把风险带到了生产环境。

这个patch的本质是**从被动响应到主动预防的切换点**——2个bug还是"正常磨合"，3个bug就是"系统性测试不足"，2个是预警阈值，3个是行动阈值。
