# atom-monitoring-coverage-drift（监控系统覆盖面随架构演进自然萎缩）

**层级**: Atomic
**ID**: atom-monitoring-coverage-drift
**触发**: 系统架构/执行方式发生变化时（技能路由→CodeAct脚本、CLI→API、单session→子session等）
**来源**: 8/23-8/30连续2周T7数据量骤降(7条/周) + 风控+全市场扫描迁到CodeAct后绕过route_log hook + 监控名存实亡

---

## 失败模式

当系统的**执行路径**发生迁移时，监控系统如果只hook了旧路径，就会出现"系统正常运行、监控显示无事发生"的假稳态。监控覆盖面随架构演进自然萎缩，但监控方浑然不觉。

### 典型场景
- 任务从"技能路由模式"迁移到"CodeAct脚本模式" → route_log不再记录 → T7监控看不到
- 任务从"子session派发"改为"主session直接执行" → 子session验收hook失效
- 工具从"CLI调用"改为"Python库直接调用" → CLI层的日志/统计hook失效
- 数据从"文件交换"改为"内存直传" → 文件系统级别的监控hook失效

### 根因

监控系统hook的是**执行路径**（某个函数/某个CLI命令/某个session类型），而不是**业务目标**。当执行路径改变但业务目标不变时，监控自动脱钩。这是"实现漂移"vs"监控锚定"的不匹配。

### 严重度

🟠 P2级——监控失效本身不会导致业务失败，但会导致问题发现延迟，从"主动发现"退化为"被动撞墙"。T7连续2周<10条阈值但没有主动发现架构漂移，就是典型后果。

---

## 约束

1. **架构变更必须同步评估监控覆盖面**：任何执行路径迁移（技能→脚本、CLI→库、子session→主session），验收条件中必须包含"监控hook是否同步迁移"这一项。**不是迁移完了才想起补监控，而是迁移前就规划好监控怎么接**。

2. **监控指标要锚定业务目标，而非实现路径**：T7应该监控"风控任务执行成功率"而非"route_log中风控条目数量"。前者是业务目标，后者是实现路径。路径变了，目标不变，监控不该断。

3. **监控数据量骤降是危险信号，不是好消息**：周/日监控数据量下降>30%或低于阈值连续2周，必须触发"覆盖面检查"，不能因为"成功率100%全绿"就麻痹。**数据少可能是系统变精简了，也可能是监控瞎了**。

4. **双路验证原则**：关键业务链路至少有两条独立的监控路径（如route_log + 结果文件mtime + 任务状态API），一条失效了另一条还能报。

---

## 为什么重要

这不是"少了几条日志"的小事——监控覆盖面萎缩会导致系统性失明。T7 Week7/8连续两周只有7条记录，成功率100%全绿，但实际风控任务每天都在跑，只是监控看不到了。如果这种情况发生在资金安全类监控上，后果会严重得多。
