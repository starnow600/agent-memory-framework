# func-memory-anchor-tiered-management（MEMORY锚点分级管理）

**层级**: Functional
**ID**: func-memory-anchor-tiered-management
**触发**: MEMORY.md容量持续逼近上限、压缩后快速反弹、状态类锚点越来越多时
**来源**: 10/3 MEMORY容量97.7%逼近上限 + 10/1压缩后2天反弹回97.7% + 10/4压到80%但趋势仍在增长 + 锚点性质混杂（核心规则/状态索引混存）

---

## 模式描述

MEMORY.md的容量问题不能靠反复压缩解决（治标不治本），必须对锚点做**分级管理**——不同性质的信息存在不同层级，核心的常驻、状态的下沉、详细内容存文件。

### 锚点三级分类体系

#### L1 核心锚点（常驻MEMORY）
- **性质**: 稳定不变、高频引用、决策必备
- **内容**: 投资硬约束🔒、核心方法论规则、关键架构状态
- **特征**: 变化频率低（周级/月级），删除会影响日常决策
- **占比目标**: ≤MEMORY容量的60%

#### L2 状态锚点（指针式下沉）
- **性质**: 动态变化、中低频引用、有时效性
- **内容**: 持仓状态、大盘Regime、风控版本、元认知阶段、行业信号
- **特征**: 每天/每周更新，过了某个时间点就不再重要
- **存放方式**: MEMORY只留"关键词+日期+文件指针"，详细内容下沉到recent_memory对应文件

#### L3 详情锚点（完全下沉）
- **性质**: 详细数据、历史记录、分析过程
- **内容**: 具体评分、计算过程、历史对话摘要、项目详情
- **存放方式**: 完全存于recent_memory/project/或decision/，MEMORY不留或仅留索引条目

### 分级管理操作流程

**Step 1: 识别（写入时判断）**
- 新增锚点时先判断属于哪一级
- L2级锚点在MEMORY中用统一的指针格式：`**关键词**：一句话状态（YYYY-MM-DD）。详见 path/to/file`
- L3级锚点不写入MEMORY，直接存文件 + 更新索引

**Step 2: 压缩（容量预警时执行）**
- 优先清理过期的L2锚点（状态已变更、时效性已过的）
- 其次精简L1锚点的措辞（不删条目，只精简表达）
- 最后考虑将L1中变化频繁的条目降级为L2

**Step 3: 巡检（周校准执行）**
- 检查每个L1锚点是否还满足"稳定+高频+决策必备"
- 将不再符合的降级为L2
- 检查L2锚点是否已过期，过期的清除指针

### 与主动压缩的关系

| 维度 | func-memory-active-compression | func-memory-anchor-tiered-management |
|------|--------------------------------|-------------------------------------|
| 定位 | 被动应急（容量快溢出时救急） | 主动治理（从结构上控制增长） |
| 方法 | 删条目 / 精简措辞 / 合并 | 分级分类 / 指针下沉 / 巡检降级 |
| 效果 | 一次性释放200-500B | 持续控制增长速度 |
| 关系 | 战术手段（治标） | 战略手段（治本） |

## 为什么有效

### 问题根源（本周完整周期验证）

10/1压缩后MEMORY从4944B→4076B（79.6%），但10/3就反弹到5001B（97.7%），不到两天涨了近1KB。根因不是"写太多"，而是**锚点性质混杂**：

- 核心规则（应该稳定）和状态锚点（每天在变）挤在同一个5KB空间
- 状态锚点不会自动过期，"iFinD连续N天空数据""S2加固期第N天"每天更新但从不删除
- 每次压缩都是"减法"，但锚点增长是"加法"，减法速度追不上加法速度

### 分级管理的价值

1. **结构上控制增长**：L2下沉后，MEMORY只存指针，具体状态存文件。新增状态不占用MEMORY空间。
2. **信息分层清晰**：核心规则是"热数据"，状态索引是"温数据"，详情是"冷数据"。各层有各自的存储和淘汰策略。
3. **压缩效率提升**：压缩时优先清理L2过期指针，比删L1核心条目安全得多。
4. **可扩展性强**：体系越成熟，需要跟踪的状态越多，分级管理让容量增长可控。

## 关键参数

| 参数 | 建议值 | 说明 |
|------|--------|------|
| L1占比上限 | 60% of MEMORY | 核心规则不应占用过多空间 |
| L2指针格式 | 统一格式 | `**关键词**：一句话状态（日期）。详见 path` |
| 容量预警阈值 | 80% | 触发L2巡检清理 |
| 容量紧急阈值 | 95% | 触发主动压缩（降级到func-memory-active-compression） |
| 巡检频率 | 每周一次（周校准） | 评估锚点级别是否需要调整 |

## Anti-pattern

- ❌ 所有锚点都往MEMORY塞（MEMORY不是笔记本，是热数据缓存）
- ❌ 压缩只删不分级（治标不治本，越压反弹越快）
- ❌ L2锚点写满详细数据（指针就该是指针，详情存文件）
- ❌ 锚点没有日期（状态锚点必须有时间戳，否则不知道新旧）
- ❌ L1锚点频繁变化（经常变的说明不是核心，应该降级为L2）
