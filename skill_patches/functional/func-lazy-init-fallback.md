# func-lazy-init-fallback

**Adapter/SDK的初始化责任从调用方收回到自身——懒初始化兜底 = 减少N个调用方各自记得init的认知负担**

## 触发条件
设计/重构适配器层（Adapter）、SDK封装、外部API客户端时；任何需要"调用方先初始化再使用"的场景

## 问题模式
初始化必须由入口脚本显式调用。当调用方有多个（cron入口、手动调用、CodeAct子任务、测试脚本……），每个调用方都得记得初始化。结果：
- 新增一个调用方就可能忘加init，导致整个流程直接炸
- 拆分/迁移代码时，init调用可能被遗漏（因为init在调用方不在adapter自身）
- 调用方需要知道adapter的内部生命周期（何时初始化、初始化什么），增加认知负担

## 懒初始化兜底模式

### 核心思想
**Adapter自己管初始化，调用方不需要知道这件事。** 第一次调用时自动检查是否已初始化，未初始化则自动执行。

### 实现要点
1. **私有状态变量**：`_mcp_available` / `_sdk_initialized` 等私有标记
2. **首次调用自动初始化**：每个公共方法入口调用 `_ensure_initialized()`
3. **幂等安全**：多次调用 `_ensure_initialized()` 无副作用
4. **失败降级**：初始化失败时标记不可用，上层走兜底链路（而非直接抛异常）
5. **可选显式初始化**：仍然提供显式init接口供性能敏感场景提前预热，但不是必须的

### 适用场景
- MCP适配器（需要先连接/鉴权的）
- 外部SDK客户端（需要先建连接的）
- 配置加载器（需要先读文件的）
- 缓存管理器（需要先建索引的）

### 不适用场景
- 初始化需要用户交互（如登录凭据）——必须显式调用
- 初始化耗时很长且影响用户体验——应该提前预热而非懒加载
- 初始化失败需要用户决策如何处理——应该显式抛出

## 为什么这是Functional层
- 这是可复用的工具组合模式——在adapter设计时应用这个模式
- 它有明确的实现要点和适用/不适用场景
- 它不是一个具体工具的使用约束（那是Atomic），而是一类组件的设计模式
