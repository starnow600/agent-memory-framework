# Functional: 代码审计+分级修复当日闭环

## Trigger
对核心系统代码（量化引擎、风控系统、记忆系统等关键基础设施）完成代码审计后，发现P0级安全/资金/数据缺陷时

## 操作模式
代码审计发现P0级缺陷后，必须当日完成修复闭环，不得拖到次日：

### 审计-修复流水线
1. **审计分级**：按P0/P1/P2/P3分级，P0=资金安全/数据失真/系统崩溃级
2. **P0当日闭环**：所有P0缺陷必须当日修复+语法校验通过，不得跨日
3. **P1打包修复**：P1级缺陷（逻辑错误但不致命）可与P0一起打包修复（改动量小则顺手做）
4. **P2/P3排期**：中低优先级缺陷纳入改进清单，按节奏推进
5. **修复报告**：修复完成后必须产出独立修复报告，逐条说明改动内容

### P0判定标准（满足任一即P0）
- 资金安全：仓位约束不校验、回撤计算错误、无交易成本
- 数据失真：收益计算口径错误、日期错位、基准偏差
- 系统崩溃：除零、数组越界、空指针等会导致程序崩溃的缺陷
- 规则违反：🔒规则在代码层未强制执行（形同虚设）

### 修复质量校验
1. **语法校验**：修复后代码必须通过语法检查
2. **口径变化声明**：如果修复导致数据口径变化（如收益从毛利变净利），必须明确标注，避免后续误判为"策略变差"
3. **边界条件验证**：修复后必须验证边界条件（零值、极值、空值）

### 跨日禁令的例外
仅当以下情况全部满足时，P0修复可跨日：
- 修复工作量≥4小时（大幅重构级别）
- 当前处于非交易时段且无近期交易计划
- 已明确标注风险和临时规避措施
- 已写入TODO并设提醒

## Why
8/10 v6.0代码审计发现30个缺陷（7个P0），整体评分仅55/100。当天完成了全部6个P0修复+语法校验+修复报告产出。证明"审计发现→当日修复"模式可行：
1. P0缺陷涉及资金安全，拖一天就多一天风险敞口
2. 审计刚做完时上下文最热，修复效率最高
3. 拖到次日需要重新进入上下文，切换成本高于连续做完
4. 修复报告与审计报告同一天产出，对照清晰，验收效率高

反观历史教训：7/10月度自检发现索引category全unknown（P0），但拖到月底才修，中间浪费了3周索引失效期。P0拖得越久，累积的损失越大。

## Source
- 8/10 v6.0代码审计：30缺陷/7P0/整体55分
- 8/10 P0修复报告：6个P0全部当日修复，语法校验通过
- 8/10 口径变化声明：收益从毛利变净利，提前标注避免误判
- 7/10 月度自检P0拖延教训：索引category全unknown拖了3周才修
- 7/24 事实验证🔒规则：用户陈述事实必须立即验证（同属"发现问题→立即处理"模式）

## Anti-pattern
- ❌ 审计完先放着，改天再修（上下文冷却+风险敞口）
- ❌ P0和P2混在一起修（优先级模糊，P0可能被拖延）
- ❌ 修复后不出独立报告（改动不可追溯，下次审计不知道改了什么）
- ❌ 口径变化不声明（数据跳变被误判为策略变化）
- ❌ 不做边界验证（修了A，崩了B）
