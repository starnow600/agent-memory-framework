# func-restore-hierarchy-verify

**系统故障恢复有层级——核心链路恢复 ≠ 全模块恢复 ≠ 数据质量达标；宣布"恢复"必须说明恢复到了哪一层**

## 触发条件
系统/模块出现故障后修复完成，需要判断"是否恢复了"并对外宣布状态时

## 问题模式
修完一个bug后只验证了核心链路能跑，就宣布"恢复了"。但实际上：
- 可能只是fast模式恢复了，full模式还没验证
- 可能核心功能通了，但某个边缘模块还是坏的
- 可能功能跑通了，但数据质量打了折扣（用了历史数据/降级数据源/缓存数据）
- 不同的人对"恢复"的定义不一样——生产者觉得"核心通了就好"，消费者觉得"和以前一样才算好"

## 三级恢复验证框架

### Level 1：核心链路恢复
- 验证：核心功能/主流程是否能跑通
- 标准：不报错、有输出、关键指标正常
- 例子：风控持仓+大盘+止损信号有数据 = L1恢复
- 宣布口径："核心链路已恢复，完整度待验证"

### Level 2：全模块恢复
- 验证：所有模块/功能是否都正常运行
- 标准：和故障前的模块清单逐一比对，不缺项
- 方法：与上一次完整版本做diff，检查"和之前比缺了什么"
- 例子：风控full模式（持仓+大盘+全市场扫描+规避损失+板块分析）全部出齐 = L2恢复
- 宣布口径："全模块已恢复，数据质量待确认"

### Level 3：数据质量达标
- 验证：产出的数据质量是否达到正常水平
- 标准：数据源是主源而非兜底、数据是实时/当日而非历史合并、完整性100%
- 例子：风控全市场扫描用iFinD当日实时数据，TOP20反映当天市场状态 = L3恢复
- 宣布口径："完全恢复"

## 验证清单原则
1. **生产者视角 + 消费者视角交叉验证**：生产者看核心指标，消费者看"和以前比缺不缺"
2. **层级不可跳跃**：不能从L1直接跳到L3，必须逐级验证
3. **降级需明示**：如果只达到L1或L2，必须明确说明哪一级没达到、为什么
4. **生产环境验证优先**：手动补跑/测试环境的验证结果不能等同于生产恢复（环境隔离可能导致差异）

## 为什么这是Functional层
- 这是可复用的诊断/验证子程序——每次系统故障恢复后都可以套用这个三级框架
- 它有明确的步骤、判定标准和宣布口径
- 它不是"怎么修bug"（那是另一个问题），是"修好后怎么确认恢复了"
