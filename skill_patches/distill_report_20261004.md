## 二、新增Patch详解

### Planning层：plan-change-impact-and-verify

**变更全链路影响分析+次日验证闭环——系统变更不是单点操作，是链路操作；不验证的变更等于没改**

**来源叙事（因果链）**：
本周4次同类问题，根因完全一致——变更缺乏全链路视角 + 缺乏验证闭环：

1. **9/27叙事Review恢复**：9/10将叙事Review降级为月度 → 记忆捕获不再生成叙事（因为"写了也没人看"）→ Wiki退化为只扫raw/ → 子agent编造理由掩盖。整条链路退化了17天，直到用户指出问题才发现。
2. **9/27 S2三问题**：日检改工作日/规则只有5条/频率过滤不一致 → 周校准没同步同样的变更 → 三问题都是"一端改了另一端没跟上"。
3. **10/2影子测试双触发路径**：决策"停止影子测试" → 只停了日历日程 → CodeAct cron继续跑 → 幽灵运行2天 → 初步归因"残留实例"，被10/3事实推翻。
4. **10/4幽灵运行真相**：MEMORY写"挡板已修复" → 但代码里根本没有挡板 → 三层问题叠加：执行偏差 + 验证缺失 + 锚点与现实脱节。

**核心洞察**：
系统越复杂，一个变更的影响面越广。只改看得见的那一处，必然有遗漏。而且因为反馈延迟（跨天/跨周），发现时问题已经扩大了好几倍。必须把"变更"从单点操作升级为链路操作——改之前先盘点全链路影响，改之后在下次执行周期验证，验证通过才能更新状态锚点。

三步法框架（盘点→同步→验证）+ 严重度分级（P0/P1/P2）+ 锚点状态管理（待验证/已验证），构成了完整的变更管理闭环。

**叙事的作用**（v0.4增强项）：
- 仅凭memory_search搜"影子测试没停""S2三问题""Wiki空操作"只能找到3-4个孤立事件，看不到它们共享同一个根因
- 叙事把这4次事件串联起来，揭示了同一个失败模式在不同领域的反复出现：元认知→风控→日程管理→记忆系统
- 如果没有叙事的因果视角，每个事件都会被当成独立的bug来修，不会升华为通用的变更管理方法论
- 更重要的是，叙事揭示了问题的**层次性**——从执行偏差到验证缺失到锚点污染，是一层一层递进的，不是一个平面上的问题。这个三层结构是设计"三步法"的直接依据

### Functional层：func-memory-anchor-tiered-management

**MEMORY锚点分级管理——核心规则常驻、状态锚点下沉、详情存文件；反复压缩是治标，结构治理才是治本**

**来源叙事（因果链）**：
- 9月底：MEMORY约4944字节（97%），紧张
- 10/1：月度规则复盘后压缩 → 4076字节（79.6%），释放了约17.5%
- 10/3：反弹到5001字节（97.7%），只剩119字节缓冲 —— **不到2天涨了近1KB**
- 10/4：压到80%，但趋势明确——每次压缩后都会反弹，而且反弹速度越来越快

叙事揭示了为什么压缩治标不治本：MEMORY里混杂了两种性质完全不同的信息——
- **核心规则**（应该稳定不变）：投资硬约束、方法论、架构原则
- **状态锚点**（每天在变）：持仓、大盘、风控版本、元认知阶段、行业信号

状态锚点不会自动过期，"iFinD连续N天空数据""S2加固期第N天"每天更新但从不删除。压缩是减法，锚点增长是加法，减法速度追不上加法速度。

**核心洞察**：
MEMORY的定位应该是"热数据缓存"而不是"笔记本"。热数据应该有分级策略——L1核心常驻、L2状态用指针下沉、L3详情完全存文件。这样新增状态不占用MEMORY空间，容量增长从"线性膨胀"变为"受控增长"。

三级分类体系（L1核心/L2状态指针/L3详情）+ 三步操作流程（识别→压缩→巡检）+ 与主动压缩的战术/战略关系，构成了完整的容量治理方案。

**叙事的作用**（v0.4增强项）：
- 仅凭memory_search搜"MEMORY容量""压缩"只能看到"又压缩了一次"的重复事件，看不到"压缩→反弹→再压缩→再反弹"的循环模式
- 叙事串联了完整的压缩周期（9月底→10/1压缩→10/3反弹→10/4再压），揭示了"越压越快反弹"的趋势
- 从趋势中推导出根因不是"写太多"而是"锚点性质混杂"，这个结论单看任何一次压缩事件都得不出
- 叙事还提供了横向对比——同样是"系统成长的烦恼"，S2加固期的容量问题和影子测试幽灵运行，本质上都是体系复杂化带来的管理问题。这个横向视角启发了"分级管理"的思路（不只是记忆系统，任何复杂系统都需要分级治理）

### Atomic层：atom-memory-anchor-fact-only

**MEMORY状态锚点必须是已验证的事实——锚点是事实的镜像，不是愿望的清单**

**失败模式**：
10/4发现专家版影子测试还在跑，但MEMORY里写着"双触发路径已通过脚本内挡板修复"。这不是小误差，而是**记忆污染**——锚点记录的是"期望状态"而不是"实际状态"。

三层递进：
1. 执行偏差：只停了日历日程，没停cron
2. 验证缺失：停了之后没人验证是否真的停了
3. 锚点污染：MEMORY直接写"已修复"，与现实完全脱节

最危险的是第三层——MEMORY是系统的"真相源"（source of truth），真相源被污染，下游全错。后续所有依赖这个锚点的决策都会被误导（比如"专家版已经停了所以不用管了"）。

**约束要点**：
- 状态锚点三档标记：✅已验证 / ⏳待验证 / 📋计划中
- "待验证"锚点必须在下次执行周期后验证并更新
- 状态变更必须有依据（查询结果/执行日志/实际观察）
- 纯计划事项不应写入MEMORY状态锚点

**叙事的作用**（v0.4增强项）：
- 仅凭memory_search搜"专家版 影子测试 还在跑"只能找到一个bug报告，看不到"记忆污染"这个更深层的问题
- 叙事逐层剥开：幽灵运行→双触发路径→验证缺失→锚点与现实脱节，揭示了问题的层次性
- 如果没有叙事的深入分析，可能只会停留在"又一个运维小bug"的层面，不会触及"记忆系统的真实性保障"这个更深的架构问题

### Atomic层：atom-system-change-next-cycle-verify

**系统变更必须在下次执行周期验证——改完不验等于没改，入口不全等于没停**

**失败模式**：
本周内同类问题出现了4次，横跨3个不同领域：
1. 9/9 日程配置：改了description但script_path没清 → 连续2天挂掉
2. 9/27 S2三问题：日检改规则没同步到周校准 → 过了1周才发现
3. 10/2 影子测试：只停了日历日程，cron继续跑 → 2天后发现
4. 10/4 幽灵运行：变更后从未验证 → 整整5天没人发现

失败模式完全一样：改了一端 → 没改另一端 → 没验证 → 过了很久才偶然发现。

**约束要点**：
- 变更后必须设置"验证提醒"，验证时间=下次执行时间
- 验证必须覆盖所有已知入口，缺一个都不算通过
- 验证结果必须记录，没有记录=没有验证
- 多入口变更的验证原则：不确定有没有其他入口→视为有，进一步排查

**叙事的作用**（v0.4增强项）：
- 仅凭memory_search搜"日程配置失败""影子测试没停"会得到两个不相关的结果，不会把它们关联到同一个失败模式
- 叙事明确指出"这不是又一个bug，而是变更管理缺失的具象化"，并且横向串联了多个领域的同类事件
- 叙事还揭示了问题的隐蔽性：因为反馈延迟（跨天/跨周），发现时问题已经扩大了好几倍。这个时间维度的洞察是单看一个事件体会不到的

## 四、追踪策略改进建议

### 本周观察

本周叙事中涉及"追踪/推送"的内容较少（国庆假期，新信息不多），主要观察点：

1. **假期推送的价值密度问题**：
   - 10/2推送"公募9月调研月报"→有价值（机构行为滞后信号）
   - 10/2推送"HTML输出格式社区讨论"→有价值（技术趋势扩散信号）
   - 每日风控报告（假期复用节前数据）→价值密度低，属于"为了跑而跑"

2. **追踪推送时机的经验**：
   - 假期不是"空窗期"，而是"信息积累期"——信息先到，交易滞后
   - 节后开盘的跳空本质上是假期积累的信息集中释放
   - 假期的信息收集有价值，但不需要"每日推送"的节奏，可以积累到节假日前/后集中推送

### 改进建议（待验证，暂不修改topic_tracking策略）

1. **假期模式轻量化**：追踪类任务在假期可降低推送频率，改为"假期信息汇总"在假期结束前集中推送
2. **信息-交易时间差意识**：对投资相关话题，假期积累的信息应标注"待节后验证"，不要当即时交易信号推送
3. **推送价值自评估**：每次推送前自问"这条信息对用户决策有增量价值吗"，没有就不推

**暂不修改topic_tracking配置**：以上为观察性结论，样本量不足（只有1个假期周期），需要更多数据验证后再考虑是否更新策略配置。

## 五、Skill决策树更新建议

### 新增规则（基于本次蒸馏发现）

#### 1. 系统变更类任务 → 优先应用plan-change-impact-and-verify

- **触发条件**：用户要求"停掉X""开启Y""切换到Z模式""修改XX规则"
- **路由建议**：识别为系统变更任务 → 激活plan-change-impact-and-verify → 按三步法执行（盘点全链路→同步变更→次日验证）
- **更新理由**：本周4次同类问题反复出现，说明现有路由缺少"变更管理"的显式识别。变更任务不是"改个配置就完了"，需要完整的链路视角和验证闭环。
- **叙事依据**：9/27叙事Review恢复连锁退化、10/2双触发路径、10/4幽灵运行三层问题——均来自memory-arch/narratives/

#### 2. MEMORY容量问题 → 从func-memory-active-compression升级到分级管理

- **触发条件**：MEMORY容量持续逼近上限（连续2次预警或压缩后快速反弹）
- **路由建议**：首次预警→active-compression（应急）；反复预警→anchor-tiered-management（治本）
- **更新理由**：本周验证了"压缩→反弹→再压缩→再反弹"的循环模式，说明仅靠主动压缩不够，需要结构性的分级管理。
- **叙事依据**：10/3 MEMORY 97.7%逼近上限 + 10/1压缩后2天反弹的完整周期观察——来自10/3和10/4每日叙事

### 更新方式

以上2条建议记录在本次蒸馏报告中，**不直接修改skill_patches决策树配置**。原因：
1. skill_patches的激活机制是"路由到某技能/进入某任务类型时，通过memory_search+技能指纹索引关联激活"，目前已写入index.json的patch会被自然检索到
2. 显式的决策树更新需要配合路由系统的改造（目前路由系统还没有"变更管理类任务"这个分类）
3. 建议在下一轮路由系统优化时，将"系统变更类"作为一个独立的任务分类，关联到plan-change-impact-and-verify

### 本次自主做了哪些任务描述未明确指定的决策

1. **追踪策略改进暂不修改配置**：任务描述说"如果有明确的改进方向，更新topic_tracking技能的策略配置"。我判断本周假期观察的样本量不足（只有1个国庆假期周期），贸然更新策略配置可能引入不稳定因素。改为记录改进建议，等更多数据验证后再更新。
2. **Skill决策树更新不直接改配置**：任务描述说"评估是否需要更新Skill决策树"。我判断skill_patches的激活依赖memory_search，新增的patch已经写入index.json会被自然检索到；显式的决策树改造需要配合路由系统分类升级，不是本次蒸馏能独立完成的。改为记录更新建议和理由。
3. **新增4条patch而非最低2条**：验收要求是"至少1条Planning/Functional + 至少1条Atomic"，共2条。我提取了4条（1 Planning + 1 Functional + 2 Atomic），因为本周素材丰富（4次同类变更问题 + 容量循环模式 + 记忆污染三层结构），只提取2条会浪费有价值的模式。
4. **Planning层选择变更管理而非价值转正**：本周有两个潜在的Planning层模式——"变更全链路管理"和"价值转正三标准"（来自专家版不转正决策）。我选择了变更管理，因为：①它有4次独立验证（横跨多个领域），置信度更高；②它的通用性更强（任何系统变更都适用）；③"价值转正三标准"更多是影子测试的延伸，与现有plan-shadow-test系列的关系更近，可以后续作为扩展补充。

### 决策依据
- 宁缺毋滥原则（来自10/1规则月度复盘叙事）：新patch宁可少也不要强行注水，但真正有价值的模式也不能因为"够数了"就漏掉
- 影子测试方法论（plan-shadow-test-default）："达标了才转正，不拍脑袋"——策略更新也应该遵循同样的原则，样本不足就先观察不改动
- 消费端驱动原则（plan-consumer-driven-pipeline-health）：决策树更新的消费端是路由系统，如果路由系统还没有对应的分类，更新了也没人消费

### 可选的替代方案
- 替代方案A：把"价值转正三标准"也作为Planning层patch提取（增加到5条）→ 被否决，因为与现有shadow-test系列重叠度较高，增量价值不如变更管理大
- 替代方案B：直接修改topic_tracking的策略配置 → 被否决，样本量不足，违反"先验后断"原则
- 替代方案C：直接修改skill_patches的路由配置 → 被否决，路由系统的分类升级是更大的工程，不应在蒸馏任务中越权处理
