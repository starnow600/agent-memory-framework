## 二、新增Patch详解

### Planning层：plan-shadow-test-accelerated-iteration

**影子测试期内加速迭代**

**来源叙事**：
- 9/3主人点破："为什么等落地再加，现在一起验证呢"——直接推动专家版v2.0在影子测试期内升级
- 风控专家版v2.0分级预警+深度分析模块在影子测试第2-3天就上线了
- v2.0.1价格口径bug修复、v2.0.3指数白名单修复——影子期内2次小版本迭代
- 第63次Review魔鬼代言人挑战：对比口径不受影响但有间接资源竞争风险

**核心洞察**：影子测试 = 安全沙箱 + 真实输入 + 对比基准。这三个条件同时满足的场景非常珍贵，不应该只是"等达标"的等待期，而应该是疯狂迭代的黄金窗口。转正时的新系统应该已经迭代了N个版本，而不是"刚上线的1.0"。

**与现有plan-shadow-test-default的关系**：基础框架（三步走）vs 进阶策略（加速迭代），互补不重复。

### Functional层：func-data-driven-dispute-resolution

**数据驱动的争议解决**

**来源叙事**：
- 9/4价值投资vs量化止损大讨论：从"二选一"到"双轨并行"的认知升级
- 止损有效性全市场回测：HS300/4年/6000次事件 → 44.4%胜率/中位数-1.35%
- 兆易卖飞案例：用户用单个案例质疑规则 → 回测数据提供全局视角
- 幸存者偏差：用户高估"错过的上涨"痛感，低估"扛到深套"概率

**核心洞察**：体系级规则争议不能停留在"我觉得vs你觉得"的层面。主动做全市场回测，用数据提供客观决策依据，讨论才能从"观点之争"升级为"基于事实的体系选择"。数据不替代决策，但提供共同的事实基础。

### Atomic层1：atom-financial-code-prefix-whitelist

**金融代码前缀必须用白名单而非宽松匹配**

**来源叙事**：
- 9/4指数判断bug：`startswith("000")` 将紫光sz000938误判为指数
- 所有000开头深市主板个股全部受影响（数百只）
- 影子测试Day5首次出现核心判断分歧 → 排查定位为代码逻辑bug
- 修复：14个核心指数白名单，主风控v6.1.1/专家版v2.0.3同步升级

**核心洞察**：金融代码体系复杂，不同类型共用前缀。宽松前缀匹配（startswith）在直觉上合理，但必然踩坑。白名单枚举是唯一安全方式，代价低收益高（P0级逻辑错误防护）。

---

### Atomic层2：atom-new-module-bug-density-alert

**新模块bug密度预警**

**来源叙事**：
- 9/3-9/4专家版v2.0 M6模块2天2个逻辑bug（价格口径+指数判断）
- 第64次Review模式识别：标记为"需关注"，"再发现1个触发阈值"
- 第64次魔鬼代言人挑战：正方说应该提前加强测试，反方说影子期发现bug是正常的
- 最终判定：2个=预警（继续观察），3个=行动（系统性测试不足）

**核心洞察**：发现bug就修是被动响应，密度预警是主动预防。2天2个bug说明测试覆盖度不足，如果等第3个再行动就是被动挨打。设立"2个预警、3个行动"的阈值，在质量问题扩大之前介入。

---

### Atomic层3：atom-shared-resource-competition-risk

**共享资源竞争风险**

**来源叙事**：
- 9/3双重故障：专家版深度分析上午耗完iFinD token → 下午主风控超限失败
- 第63次Review魔鬼代言人挑战3：深度分析的搜索调用可能间接影响iFinD配额 → 影响基准版数据获取（隐性风险）
- 三级兜底解决了"数据源挂了怎么办"的问题，但没有解决"自己人抢资源"的问题
- 9/3 trace洞察："风控数据源的脆弱性——两个独立数据源同时挂概率低但一旦发生是致命的"

**核心洞察**：新增功能时很容易忽略它会消耗和核心系统共享的资源。增量功能消耗过大时，会影响甚至拖垮核心系统——这不是增量功能本身的bug，是资源竞争导致的连锁故障。上线前必须评估共享资源消耗，核心系统资源优先级更高。

### 3. 金融代码前缀白名单的领域知识
**怎么发现的**：9/4的bug发现过程很有戏剧性——专家版和基准版出现分歧 → 以为是专家版bug → 修复后重跑发现专家版反而是对的 → 真正的bug是指数判断逻辑。这条曲折的排查路径，加上"所有000开头深市个股全部受影响"的大范围影响，让这个教训特别深刻。

**如果只用memory_search**：可能只找到"指数判断bug已修复"的事实记录，但不会有"宽松前缀匹配在金融领域必踩坑"的模式提炼。

**叙事的价值**：bug的发现过程（曲折排查）、影响范围（数百只个股）、发现机制（影子测试对比才暴露）——这些上下文让一个普通的bug升级成了一个通用的编程约束。

### 4. 新模块bug密度的阈值意识
**怎么发现的**：第64次Review的模式识别部分明确列出了"专家版新模块bug"的计数（2次）和判定（⚠️需关注，再1个触发阈值）。魔鬼代言人的正反方辩论（正方：应该提前加强测试；反方：影子期发现bug是正常的）——逼着你设定了明确的阈值（2个=预警，3个=行动），而不是模糊的"好像有点多"。

**如果只用memory_search**：只能找到"价格口径bug已修复"、"指数判断bug已修复"两个独立事件，不会有"bug密度"这个概念，更不会设定预警阈值。

**叙事的价值**：review的"同类错误≥3次"计数框架 + 魔鬼代言人的正反辩论 = 提炼出了明确的质量预警机制。这是叙事+元认知双重作用的结果。

### 5. 共享资源竞争的连锁故障模式
**怎么发现的**：把9/3的"iFinD日token超限"和"专家版深度分析上线"放在同一时间线上看，才能看到因果关系——不是iFinD自己不稳定，是我们自己新增的模块把配额用完了，连累了核心系统。第63次Review魔鬼代言人挑战3也指出了这个"间接资源竞争风险"。

**如果只用memory_search**：只会找到"iFinD超限后切换到三级兜底"的解决方案记录，看不到"增量功能消耗共享资源影响核心系统"这个根因模式。

**叙事的价值**：时间线上的因果链（深度分析上线 → 调用量激增 → token耗尽 → 主风控失败），以及review的元层面反思（"对比口径本身不受影响，但存在间接资源竞争风险"）——共同揭示了这个隐蔽的系统级风险。

## 五、Skill决策树更新建议

### 建议1：plan-shadow-test-default 增加"加速迭代"子阶段

**更新理由**：来自 plan-shadow-test-accelerated-iteration（本周新增Planning层patch）。原影子测试三步走框架（并行跑→达标转正→旧版降级）缺少"影子期内加速迭代"的明确指引，导致默认思维是"影子期只验证不升级"，浪费了宝贵的试错窗口。

**建议更新内容**：在plan-shadow-test-default的"三步走框架"之前或之间，增加"加速迭代期"的说明：
- 影子测试前半段（第1-2周）：鼓励增量迭代，发现问题立即修、有价值的功能立即加
- 影子测试后半段（第3-4周）：收敛稳定，停止新增功能，确保最终验收版本稳定
- 约束：增量必须模块化，不影响核心对比口径

**关联叙事**：9/3主人点破"为什么等落地再加" + 专家版v2.0影子期内升级的成功先例 + 第63次Review魔鬼代言人关于对比口径的挑战

---

### 建议2：func-fact-verification-closure 扩展为"数据驱动决策支撑"

**更新理由**：来自 func-data-driven-dispute-resolution（本周新增Functional层patch）。原事实验证闭环只处理"用户陈述事实的验证"（如用户说"股价50元"要验证对错），但本周发现了一个更大的场景——用户质疑规则/体系时，主动提供数据回测作为决策依据。这是事实验证的升级版：从"验证对错"到"提供量化决策依据"。

**建议更新内容**：
- func-fact-verification-closure 保留（处理事实性陈述验证）
- func-data-driven-dispute-resolution 作为独立patch（处理体系级分歧的数据支撑）
- 两者关联：前者是微观事实验证，后者是宏观规律验证，构成完整的数据支撑体系

**关联叙事**：9/4止损有效性回测 + 价值投资vs量化止损讨论升级 + 7/26事实验证🔒首例闭环（微观版本的历史先例）
