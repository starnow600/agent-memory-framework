## 一、适用范围

满足以下任一条件即触发变更管理流程：

1. **功能启停**：开启/关闭/暂停/恢复任何自动化任务
2. **规则变更**：修改风控规则、阈值、频率、扫描范围
3. **数据源/工具切换**：切换主数据源、新增/移除数据通道
4. **调度方式变更**：修改日程、cron、触发条件
5. **架构调整**：脚本拆分、模块重组、配置格式变更

### 严重度分级

| 级别 | 定义 | 影响分析深度 | 验证要求 |
|------|------|-------------|---------|
| **P0** | 核心功能启停 / 核心规则变更 | 全链路盘点（入口+依赖+状态） | 次日+3日双重验证 |
| **P1** | 非核心功能变更 / 数据源切换 | 入口盘点 + 主要依赖 | 次日验证 |
| **P2** | 参数微调 / 文案修改 | 检查相关配置项 | 改完即时验证 |

## 二、变更三步法

### Step 1: 变更前 — 全链路影响分析

**必须输出变更清单**，覆盖三个维度：

| 维度 | 检查项 |
|------|--------|
| **触发入口** | 日历日程 / CodeAct cron / 脚本内调用 / 其他任务联动钩子 / 手动触发入口 |
| **依赖关系** | 上游数据源 / 下游消费者 / 监控项 / 文档锚点 / 其他脚本引用 |
| **状态记录** | MEMORY锚点 / route_log / S2自检规则 / Wiki页面 / 索引 |

**Anti-pattern**：
- ❌ 变更描述只有一行（"停掉影子测试"太粗）
- ❌ 只看最显眼的入口，忽略其他路径
- ❌ 忽略状态记录的同步更新

### Step 2: 变更中 — 同步所有相关方

- 按变更清单逐个修改，**不遗漏任何入口**
- 启停类变更，**优先加挡板/开关**而非直接删除（挡板可验证、可回滚）
- MEMORY锚点标注 **⏳ 待验证** 状态，不得直接写"已完成"
- 涉及多文件修改的，改完跑语法检查/单元测试

### Step 3: 变更后 — 验证闭环

| 变更类型 | 验证标准 |
|----------|---------|
| **启停类** | 查询所有触发入口状态，确认全部处于目标状态（缺一不算通过） |
| **配置类** | 实际运行一次，确认运行时读取的值与预期一致 |
| **模式切换类** | 实际运行一次，确认输出/行为符合新模式，无旧模式残留 |
| **代码修改类** | 对比修改前后的输出，差异在预期范围内 |

**验证结果必须记录**：
- ✅ 通过 → 更新锚点状态 + 附验证依据
- ❌ 不通过 → 立即排查 + 记录原因 + 重新变更 + 设置下一次验证
- ⏳ 待验证超2个周期 → 视为异常，主动排查

## 三、锚点写入规则

### 状态三档标记

MEMORY中的状态锚点必须明确标注状态：

- **✅ 已验证**：经过实际验证的事实，附验证依据
- **⏳ 待验证**：已执行变更，尚未验证是否生效
- **📋 计划中**：不写入MEMORY，存于todo/decision文档

### 禁止写入MEMORY的内容

- 纯计划事项（存recent_memory/todo/）
- 未验证的推测/假设
- 别人说的"已经好了"（必须自己验证）
- 愿望式描述（"应该好了""估计没问题"）

## 六、Anti-pattern 清单

变更时对照检查，命中任何一条 = 变更不合格：

1. ❌ 只改了一个入口，没盘点其他路径
2. ❌ 改完就更新锚点为"已完成"，跳过验证
3. ❌ 锚点写"已修复"但没有验证依据
4. ❌ 发现异常时用"残留实例""可能是缓存"等侥幸解释，不排查根因
5. ❌ 变更清单只有一行描述，没有全链路盘点
6. ❌ "待验证"锚点挂着超过2个周期不更新
7. ❌ 把计划中的事写成已完成（愿望式写作）
