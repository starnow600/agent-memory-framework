## 背景

月度自检报告提出"expires_at大面积失效（健康度63.4%）"列为P0-2问题。用户指出：

1. 已有decay降权机制，为什么还需要时间维度的过期标准？
2. 如果要做，为什么不能跟着权重走，而要按类型拍脑袋定过期时间？

查证后确认：
- 当前记忆索引仅112条，规模远未到需要硬过期瘦身的程度
- 按类型定过期时间是拍脑袋，没有依据
- 基于使用频率/权重的降级机制才是更合理的方向

## 决策

**暂不处理**。当前规模（~100条）下decay机制足够，expires_at不是P0问题。

**设置触发阈值**：当记忆索引条目数达到 **1000条** 时，启动基于权重的记忆降级机制设计与实施。

## 基于权重的降级方案（方向，待设计）

核心原则：不按"出生时间"过期，按"使用频率"降级。记忆该留在哪个层级，取决于它还有没有被用到，而不是存了多久。

### 机制方向（待详细设计）
1. 每次记忆被访问（搜索命中/读取引用），权重+1或刷新时间戳
2. decay机制定期给所有记忆降权重
3. 权重低于阈值A → 从即时层沉到近中期
4. 权重低于阈值B → 从近中期沉到长期层（仅在图谱中，不进主动索引）
5. 永不硬删，只是访问层级越来越深

### 取消的方向
- 按记忆类型（规则类/决策类/trace类）拍脑袋定过期时间 → 不做

## 触发条件
- 记忆索引条目数 ≥ 1000
- 或检索效率明显下降（用户感知/系统监控均可触发）

## 触发后行动
1. 记忆类型普查 + 访问频率统计
2. 权重算法设计 + 阈值设定
3. 降级机制实施
4. 索引同步脚本改造
