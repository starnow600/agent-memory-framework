# 元认知规则生长机制设计

**创建日期**: 2026-08-30
**状态**: 方案设计完成，待落地
**设计依据**: 微软行为规则闭环（主线）+ MARS双路径反思（成功/失败双提取）+ EvolveR质量评分（生命周期管理）

---

## 一、设计目标

解决当前核心问题：**记忆系统只会存事件，不会主动提炼模式；规则都是踩坑后被动加的，成功的做法不会升级为默认方法论。**

具体目标：
1. 规则从"散文式"升级为"结构化"——每条有来源、有范围、有评分、有生命周期
2. 从"单路径（失败→禁令）"升级为"双路径（失败禁令 + 成功策略）"
3. 从"只加不减"升级为"有进有出、质量可控"
4. 从"被动触发"升级为"主动发现+月度生长复盘"

---

## 二、规则结构化 Schema

每条规则必须包含以下字段，新增规则时缺字段不算正式规则。

```
RULE ID:        R-XXX（三位数字，从R001开始递增）
TYPE:           prohibition（禁令型） / strategy（策略型）
CATEGORY:       投资风控 / 记忆系统 / 任务执行 / 沟通协作 / 技能工具 / 其他
TRIGGER:        触发来源（human_review / self_discovery / incident_fix / success_pattern）
SCOPE:          适用范围（什么场景下生效）
RULE_CONTENT:   规则正文（一句话说清楚）
RATIONALE:      为什么要有这条规则（背后的逻辑）
EVIDENCE:       证据链（来源事件/决策文档/对话记录）
ADDED_DATE:     加入日期
QUALITY_SCORE:  质量分（EvolveR拉普拉斯平滑：(成功次数+1)/(使用次数+2)）
USE_COUNT:      使用次数（每次调用+1）
SUCCESS_COUNT:  成功次数（用了之后结果好+1）
STATUS:         active / deprecated / experimental
CHECKLIST_ITEM: 关联自检清单编号（C-XX）
```

**TYPE字段说明**：
- **prohibition（禁令型）**：不能做什么。当前MEMORY.md里大部分是这类。
- **strategy（策略型）**：应该怎么做更优。影子测试方法论、双轨验证等属于这类。

## 三、双路径提取规则

### 路径A：失败 → 禁令型规则（现有路径，保留）

**触发条件**（满足任一）：
1. 你明确指出"这是第N次了"——重复出现的同类问题
2. 出了需要修复的bug/事故（如手误数据、任务跑一半）
3. 违反了已有硬约束但未被检测到（如亏损补仓没被自动发现）

**提取标准**：
- 不是一次性的笔误或偶发事件
- 在其他场景下**可能再次发生**
- 有明确的"不要做什么"或"必须做什么"的边界

### 路径B：成功 → 策略型规则（新增路径）

**触发条件**（满足任一）：
1. 同一类成功做法**重复出现≥3次**（影子测试、双轨验证、渐进式上线……）
2. 你明确说"以后就这么做"
3. 一个方法在多个不同场景下验证有效

**提取标准**：
- 不是具体任务的成功，而是**方法层面**的可复用策略
- 有明确的"适用场景 + 操作步骤 + 预期效果"
- 能从"这次这么做了"抽象成"以后类似情况都这么做"

### 双路径对比

| 维度 | 路径A（禁令型） | 路径B（策略型） |
|---|---|---|
| 来源 | 失败/错误/踩坑 | 成功/有效做法/重复模式 |
| 数量（当前） | ~15条 | ~3条（严重不足） |
| 增长速度 | 快（出事了就加） | 慢（需要≥3次重复才提炼） |
| 价值 | 防退化（不犯老错） | 促进化（用更好的方法） |
| 主动程度 | 被动（出事了才加） | 主动（需要主动发现模式） |

**目标比例**：长期来看 禁令型:策略型 ≈ 6:4 比较健康。当前估计是 9:1。

## 四、质量评分与生命周期

### 评分公式（借鉴EvolveR）

```
quality_score = (success_count + 1) / (use_count + 2)
```

- 拉普拉斯平滑，避免冷启动时极端值
- 新规则默认 use_count=0, success_count=0 → score=0.5（中性）
- 每次用到这条规则，use_count +1
- 用完之后结果好（任务顺利/你没提意见/目标达成），success_count +1
- 用完之后出问题了，success_count 不加

### 生命周期状态流转

```
experimental（实验期）
    ↓ 使用≥3次且score≥0.7
active（生效）
    ↓ score≤0.3 或 连续3个月没用
deprecated（降级观察）
    ↓ 再观察1个月仍无改善
removed（移除归档）
```

**状态说明**：
- **experimental**：新加的规则，先试运行，不强制。用几次看看效果再说。
- **active**：正式生效，必须遵守。进MEMORY.md主列表。
- **deprecated**：效果不好或者长期不用，降级观察，不强制执行。
- **removed**：从主列表移除，归档到历史规则文件，不再使用。

## 五、规则生长流程

### 5.1 日常触发（随时）

**路径A触发**：
- 出了错/你指出问题 → 24h内判断是否值得加规则
- 值得 → 按schema写好，标experimental → 进候选池
- 不值得 → 记录但不加规则

**路径B触发**：
- 做任务时发现"这好像是第N次用同一种方法了" → 标记候选
- 你说"以后就这么做" → 直接进候选池
- 累计到≥3次 → 提炼成策略型规则，标experimental

### 5.2 月度生长复盘（每月底，暂手动执行）

**步骤**：

**Step 1：模式扫描**
- 扫当月decision文档、任务记录、对话摘要
- 路径A：本月踩了哪些坑？哪些是重复出现的？
- 路径B：本月哪些做法反复成功？哪些方法跨场景复用了？
- 产出：本月候选规则清单

**Step 2：候选评审**
- 每条候选按schema补全字段
- 评估：是否满足"可复用、边界清晰、有证据"三条件
- 产出：新增experimental规则列表（每月最多2-3条，宁缺毋滥）

**Step 3：存量复审**
- 所有active规则过一遍
- use_count更新（本月用到了几次？效果如何？）
- quality_score重算
- 状态判断：是否有需要降级的？有没有experimental可以转正的？
- 产出：规则状态变更列表

**Step 4：自检清单同步**
- 新增规则对应加进自检checklist
- 降级/移除的规则从checklist里拿掉
- 产出：更新后的自检清单

**Step 5：MEMORY.md同步**
- active规则同步到MEMORY.md（保留精简版，不把全schema塞进去）
- 完整schema存在规则库文件里
- 产出：更新后的MEMORY.md

## 六、自检 Checklist 机制

### 设计原则

不是所有规则都进checklist，只进"执行前需要主动检查"的规则。纯粹是知识型的（比如"反转30-40分胜率最高"）不进checklist，进知识库。

### Checklist分类

| 类别 | 编号 | 检查时机 | 示例 |
|---|---|---|---|
| 任务启动前 | C-T0xx | 派子session/启动大任务前 | 子任务验收制、大任务确认制 |
| 投资决策 | C-I0xx | 买卖/风控/仓位操作前 | 影子测试默认、止损区分逻辑 |
| 记忆操作 | C-M0xx | 加规则/改记忆/删东西前 | 决策即记录、压缩必留痕 |
| 交付前 | C-D0xx | 给用户交付产物前 | 产物存在性检查、数据准确性验证 |
| 工具使用 | C-U0xx | 调用工具前 | 🔒规则强制执行、先验证后判断 |

### 执行方式（初期手动，后续可自动化）

- 不同场景触发对应类别的checklist
- 不是每次全部过一遍，而是按任务类型取相关项
- 比如做投资决策 → 自动调出C-I类所有项过一遍
- 比如派子session → 自动调出C-T类所有项过一遍

## 九、边界与风险

### 不做什么
- 不搞模型微调/元优化（太重，性价比低）
- 不搞双层元认知架构（MCTR那种，不适用）
- 不搞RL强化学习（没有合适的奖励信号）
- 不自动修改规则（所有规则变更都经过你确认）

### 风险与应对

| 风险 | 应对 |
|---|---|
| 规则太多记不住 | active规则总量控制在20条以内；超了就合并/降级 |
| 路径B提炼不准，加了垃圾策略 | experimental期严格评审，每月最多加2条，转正需≥3次验证 |
| 月度复盘变成形式主义 | 每次复盘必须有明确产出（新增/降级/转正的具体规则），空转就停 |
| 质量评分主观（success_count怎么算） | 初期粗粒度：你没提意见就算成功；等有更明确的反馈机制再细化 |

## 十、三层闭环落地方案

### 总览

```
┌─────────────────────────────────────────────────────┐
│  上游：记忆捕获 + 元标签（原料供给）                   │
│  每条记忆打 type / feedback_subtype / repeat_count   │
│  产出：结构化的记忆原料，不再是散文                   │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  中游：规则库 + 生命周期管理（质量控制）               │
│  双路径提取 → 质量评分 → 状态流转                     │
│  产出：高质量、可追溯、有进有出的规则库               │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  下游：场景触发式自检（执行落地）                     │
│  进入对应场景时，自动调出相关规则过一遍               │
│  产出：规则真正被使用，而不是躺在文件里               │
└──────────────────────┬──────────────────────────────┘
                       ↓
            使用记录 → 反哺中游评分（闭环）
```

### 10.1 上游：记忆捕获 + 元标签

**改动位置**：每日记忆捕获脚本

**改动内容**：每条捕获的记忆，追加3个元标签字段。

#### 标签1：type（必打，5选1）

| type值 | 含义 | 示例 |
|---|---|---|
| `fact` | 事实信息 | "长川半年报营收增长30%" "Regime处于BEAR" |
| `rule` | 规则/方法论 | "影子测试默认方法论" "反转30-40分甜区" |
| `feedback` | 用户反馈/纠正 | "不要拍脑袋，先查证" "直接点别废话" |
| `decision` | 决策记录 | "方案B不做方案C" "紫光补仓200股" |
| `pattern` | 观察到的行为模式 | "连续3次用了双轨验证" "你喜欢结论先行" |

**判断规则**：
- 一条记忆可以有多个type（比如既是decision又是rule），但必须有主type
- 拿不准的时候默认fact，不强行归类

#### 标签2：feedback_subtype（type=feedback时）

| subtype值 | 含义 | 触发关键词 |
|---|---|---|
| `evidence_first` | 先查证/别拍脑袋/要证据/数据呢 | "拍脑袋""证据""查证""确认一下""先搜""数据呢""来源呢" |
| `be_direct` | 直接点/别废话/结论先行 | "直接说""别绕""结论是什么""说重点" |
| `no_assumption` | 别假设/先确认/想当然 | "别假设""先确认""想当然""你确认过吗" |
| `quality_issue` | 质量问题/不仔细/手误 | "手误""错了""不准确""再检查一下" |
| `process_issue` | 流程问题/漏步骤 | "漏了""怎么没有""还差一步" |
| `open_category` | 新类别，待定 | 匹配不上以上任何一类 |

**判断规则**：
- 关键词匹配 + 语义判断
- 匹配不上先放open_category
- 同一open_category累计≥2次，升级为新的正式subtype

#### 标签3：repeat_count

- 对type=feedback且subtype相同的记忆，维护一个累计计数
- 每次新增同类反馈，计数+1
- **≥3次触发阈值**：自动标记"候选规则"，进入月度生长复评审的待处理列表
- 计数记录在 `rules/feedback_counter.json`

#### 上游产出物

- 带标签的记忆条目（写入每日记忆捕获产物）
- `rules/feedback_counter.json`（反馈类别计数）
- 候选规则自动标记（≥3次的反馈类别）

#### 改动量评估

- 记忆捕获脚本新增标签分类逻辑：约50-80行
- 新增feedback_counter.json读写逻辑：约20行
- 总计：小改动，1小时内可完成

### 10.2 中游：规则库 + 生命周期管理

**位置**：`memory-arch/rules/` 目录

**目录结构**：
```
rules/
├── rules_index.json          # 规则总索引（id/type/status/category/更新时间）
├── prohibition_rules.json    # 禁令型规则库
├── strategy_rules.json       # 策略型规则库
├── feedback_counter.json     # 用户反馈计数（上游写入，中游读取）
├── usage_log.json            # 规则使用日志（下游写入，中游读取）
└── initial_screening_report.md  # 初筛报告
```

#### 双路径提取（规则来源）

| 路径 | 来源 | 触发机制 | 产出 |
|---|---|---|---|
| A-禁令 | 失败/错误/踩坑 | 出事了 → 24h内判断 → 加规则 | prohibition型 |
| B1-成功模式 | 重复出现的有效做法 | decision文档扫描 + 人工识别 | strategy型 |
| B2-重复纠正 | 用户反复纠正同一件事 | feedback_counter ≥3次 自动触发 | strategy型 |
| B3-反向推导 | 从禁令反向推导正向策略 | 月度复盘中人工提炼 | strategy型 |

**B2路径是新增的核心自动化点**：上游打标签→计数→≥3次自动进候选池→月度复评审。

#### 质量评分公式

```
quality_score = (success_count + 1) / (use_count + 2)
```

- 拉普拉斯平滑，新规则默认score=0.5（中性）
- use_count：下游每次使用+1（写入usage_log.json）
- success_count：使用后结果好+1（任务顺利/用户没提意见/目标达成）

#### 生命周期状态流转

```
experimental（实验期）
    ↓ 使用≥3次 且 score≥0.7
active（生效）
    ↓ score≤0.3 或 连续2个月使用次数=0
deprecated（降级观察）
    ↓ 再观察1个月仍无改善
removed（归档移除）
```

#### 管理节奏

**月度生长复盘**（手动触发，暂不接入月度自检）：

| 步骤 | 内容 | 产出 |
|---|---|---|
| 1 | 扫描feedback_counter，≥3次的提取为候选规则 | 候选规则清单 |
| 2 | 扫当月decision文档，找成功模式 | 候选规则清单 |
| 3 | 从禁令反向推导正向策略 | 候选规则清单 |
| 4 | 候选评审：补全schema+质量初评 | 新增experimental规则（每月≤3条） |
| 5 | 存量复审：更新use_count/success_count/score | 状态变更列表 |
| 6 | 转正/降级/移除决策 | 最终规则库 |
| 7 | 同步更新MEMORY.md（active规则精简版） | 更新后的MEMORY.md |

#### 中游产出物

- 结构化规则库（prohibition + strategy）
- rules_index.json（总索引）
- 月度生长复盘报告
- 更新后的MEMORY.md（active规则精简版）

### 10.3 下游：场景触发式自检

**核心原则**：不是所有规则全过一遍，而是**进入某类场景时，调出对应类别的规则过一遍**。

#### 试点场景（2个，Phase B验证期）

| 场景ID | 场景名称 | 触发时机 | 自检规则 |
|---|---|---|---|
| S1 | 交付前自检 | 给用户输出事实/数据/结论前 | S009先验后断 + S010交付数据自证 + R0xx用户确认数据 |
| S2 | 子任务返回验收 | 子session返回后、交付给用户前 | R0xx子任务验收制 + 产物存在性检查 + 目标对齐检查 |

#### 扩容场景（试点通过后追加）

| 场景ID | 场景名称 | 触发时机 | 自检规则 |
|---|---|---|---|

#### 自检执行方式

每个场景的自检清单包含3-5条检查项，每条是一个Yes/No问题：

**S1 交付前自检清单示例**：
- [ ] 结论有没有查证？来源链接或依据是什么？
- [ ] 关键数据有没有核对过原始数据/报告？
- [ ] 是不是结论先行、再说依据？

**S2 子任务返回验收清单示例**：
- [ ] 验收标准逐条过了吗？每条都达标？
- [ ] 产物文件存在吗？路径对吗？可读吗？
- [ ] 结果和原始目标对齐了吗？有没有跑偏？

#### 使用记录

每次自检记一条到 `rules/usage_log.json`：
```json
{
  "date": "2026-09-01",
  "scene": "S1",
  "rules_checked": ["S009", "S010"],
  "found_issue": true,
  "issue_description": "数据未核对原始报告",
  "was_real_issue": true,
  "time_spent_seconds": 45
}
```

字段说明：
- found_issue：自检时有没有发现问题
- was_real_issue：后来确认是不是真问题（用于计算误检率）
- time_spent_seconds：本次自检花了多少秒

#### 下游产出物

- usage_log.json（规则使用日志）
- 每个场景的自检checklist（轻量文档）

### 10.4 闭环：数据流动

```
上游（记忆捕获打标签）
    ↓ feedback_counter
中游（月度生长复盘）
    ↓ 新增/转正/降级规则
下游（场景触发式自检）
    ↓ usage_log → use_count / success_count
中游（重算quality_score → 状态流转）
    ↓ 规则质量变化
下游（更精准的规则集合）
```

三层互相喂数据，形成自加强闭环。

### 10.6 边界与不做清单

- ❌ 不搞模型微调/元优化（太重）
- ❌ 不搞双层元认知架构（不适用）
- ❌ 不搞RL强化学习（没有合适奖励信号）
- ❌ 不自动修改规则（所有规则变更需用户确认）
- ❌ 初期不接入月度自检（先手动跑，验证价值后再正式化）
- ❌ 不自检所有规则（只按场景触发3-5条，避免过度检查）
