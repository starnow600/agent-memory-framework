# PlugMem L0 摘要预取改造决策

**日期**：2026-08-23
**类型**：架构变更（记忆系统）
**状态**：已完成，当日生效

---

## 背景

8/23 每周探索报告（第20周）发现 OpenViking（火山引擎开源 Context Database，3.1万星）的三层上下文模型（L0摘要/L1概览/L2全文）与主人 PlugMem 三层架构高度同构。

报告提出 P1 建议：**PlugMem 引入"L0摘要预取"机制**。

主人质疑："L0 摘要预取机制为什么我记得有类似的机制"——经查证，PlugMem 确实已有 L0 层，但存在严重问题：

| 问题 | 具体表现 |
|------|---------|
| 存储内容错位 | L0 只存最近 2 session 的原始对话文本，与事实查询需求不匹配 |
| 与 L2 重复 | 对话内容 L2 也有，L0 无独特价值 |
| 路由不优先 | ROUTING_POLICY 中 cat 1 (single_hop) 不走 L0 |
| 实际贡献为零 | L0 命中率 0%，L0 贡献度 0% |

**结论**：L0 层名义上存在，但形同虚设。需要的是"改造"不是"新建"。

---

## 决策内容

### 选择方案
**L0 层从"原始对话暂存区"改造为"结构化摘要热缓存"**

核心变更：
1. **存储结构**：从原始对话文本 → 结构化摘要（summary + key_facts + entities + tags + importance + value）
2. **路由策略**：cat 1 (single_hop) 从 L1→L2→L0 改为 L0→L1→L2，命中即返回（快路径）
3. **预取机制**：L1/L2 检索结果自动提炼摘要写入 L0（importance≥3 且不存在时）
4. **LRU 淘汰**：L0 容量 50 条，冷条目自动淘汰

### 决策依据
1. **L0 层已存在但贡献为零**——不是重复建设，是修复已有架构的无效层
2. **OpenViking 验证了方向**——行业级开源项目采用相同的三层模型，说明架构思路正确
3. **收益明确**：查询速度提升、L0 层真正发挥作用、Recall 不下降
4. **工作量可控**：仅修改 L0 存储和路由逻辑，不影响 L1/L2 现有功能
5. **不破坏现有索引**：L1 索引和 L2 Wiki 完全不动，风险低

### 替代方案
- **直接移除 L0 层**：简化架构，但失去了"热缓存加速"的潜在收益，与行业趋势背道而驰
- **维持现状**：L0 继续 0% 贡献，纯浪费容量
- **一步到位做 LLM 摘要生成**：成本高、依赖外部模型，当前阶段用启发式规则即可

|------|--------|--------|------|
| L0 命中率 | 0% | 100% | +100pp ✅ |

| Recall@10 | 94.53% | 94.87% | +0.34pp |
| Recall@5 | 86.17% | 88.17% | +2.00pp ✅ |

Benchmark：D2 LoCoMo 风格事实检索，50 条查询 / 132 条语料。
