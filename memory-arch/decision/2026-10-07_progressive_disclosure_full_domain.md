# 渐进式披露全域覆盖决策

**日期**：2026-10-07
**类型**：架构变更 / 项目里程碑
**状态**：⏳ 待10/8生产验证
**决策文件**：memory-arch/decision/2026-10-07_progressive_disclosure_full_domain.md

## 决策背景

10/6启动渐进式披露开发时，初始范围仅限风控脚本（D1：配置分离+数据层拆分）。用户两次指出问题：
- "这个只有风控，其他技能的渐进披露呢？"
- "你依然只盯着风控，但渐进式披露不应该只覆盖风控"

**根因**：惯性思维——"风控是大头先啃风控"，但渐进式披露是架构原则，不是风控专属优化。

## 决策内容

### 1. 范围扩展：从"风控优化"升级为"全域架构原则"

扩展至全域9个模块：

| 模块 | 分类 | 形态 | 状态 |
|------|------|------|------|
| 风控主脚本 | 代码 | 配置分离+数据层拆分 | ✅ D1完成（2992行，-20.4%） |
| 风控专家版 | 代码 | 复用共享配置+数据层模块 | ✅ 完成（2855行，-6.3%，消除200行重复） |
| S2日检 | 代码 | 探测规则独立模块 | ✅ 完成（s2_probe_rules.py 225行） |
| S2周校准 | 代码 | 复用统一探测规则 | ✅ 完成（659行，-17.8%，消除重复定义根因） |
| MEMORY锚点 | 数据 | T0/T1/T2三级分级 | ✅ 已完成（90%→68.8%） |
| 记忆图谱 | 数据 | 增量更新 | ✅ 已实现 |
| LLM Wiki | 数据 | 增量编译 | ✅ 已实现 |
| Skill指纹路由 | 架构 | 按需加载Skill | ✅ 已完成（Skill级） |
| 规则文件 | 架构 | 索引+按需读取 | ✅ 已有机制（rules_index.json） |

### 2. 扫描引擎拆分延后

- **原计划**：10/7 D2 拆分扫描引擎（~1350行）+ 报告生成（~400行）
- **决策**：延后至10/8生产验证通过后再做
- **理由**：
  1. `run_market_scan` 340行是核心流程，依赖关系复杂，拆分风险高
  2. 10/8是节后首个交易日实跑，生产稳定性优先级最高
  3. 核心收益（按需加载）已通过配置分离+数据层拆分实现
  4. 扫描引擎+报告生成属于"深度优化"，不影响架构正确性

### 3. S2探测规则统一

- 创建 `s2_probe_rules.py` 为单一事实来源
- S2日检和周校准都引用此模块
- **解决的问题**：W13发现的"变A忘B"典型场景——专家版从影子测试切换到副驾驶模式后，S2日检规则更新了但周校准没同步
- **方法论价值**：从"靠人记住不要忘"到"靠架构保证不会忘"

## 影响分析

### 正向影响
1. **全域一致性**：9个模块统一遵循渐进式披露原则，不再有"风控特化"的偏见
2. **消除变更管理盲区**：S2日检+周校准共用规则，从根因上解决"改一处忘一处"
3. **代码复用**：专家版复用主风控数据层，消除~200行重复代码
4. **风险可控**：扫描引擎拆分延后，不影响10/8生产验证

### 风险
1. ⚠️ 专家版去重后未做完整验证——需在10/12周日专家版运行时验证
2. ⚠️ 扫描引擎未拆——MCP Tasks幂等化需要断点续跑能力，可能要等W14
3. ⚠️ 规则文件索引是10/1生成的，新增的change_management.md等是否已纳入需确认
